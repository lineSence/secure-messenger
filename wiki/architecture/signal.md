# Шифрование 1:1 — `sm-signal` (libsignal)

Код: `crates/sm-signal/`. Решения: ADR-1, ADR-2, ADR-47, ADR-55, ADR-60. Пункт 3 плана `0.0.1-alpha` (`wiki/workflows/releases.md`).

| Что | Как |
|---|---|
| Библиотека | `libsignal-protocol` из `signalapp/libsignal`, тег v0.105.0 = коммит `4beb029d8a94…` (в `Cargo.toml` — `rev`, cargo не даёт указать тег и коммит вместе); постквантовый ратчет `spqr` v1.6.0 из `signalapp/SparsePostQuantumRatchet` |
| Протокол | начало сессии — PQXDH (X25519 + Kyber1024), сообщения — Double Ratchet со SPQR; своя криптография не пишется (ADR-1) |
| Случайные числа | только `OsRng` (`rand` 0.9, функции `os_rng`) |
| Асинхронность | трейты хранилищ libsignal асинхронные; наши хранилища синхронные, поэтому будущее выполняется сразу (`now_or_never`), исполнителя нет; «не готово» — ошибка `Pending` |
| Самопроверка | `self_check()` — полный круг в памяти через наши хранилища (`MemKv`): карточка Боба, сессия Алисы, первое сообщение, ответ, ещё одно сообщение; входит в `core_self_check()` в `sm-ffi` — при сбое приложение не открывает экраны (`CoreState.Broken`) |
| Сборка | `protoc` нужен `prost-build`: `scripts/fetch-protoc.sh` скачивает protobuf v36.2 и сверяет sha256 (CI — задача `rust`; Android — `build-android-core.sh`) |
| Проверка поставок | `deny.toml`: `allow-git` — два репозитория Signal; примитивы — только как прямые зависимости крейтов Signal и внутренних связей RustCrypto (`wrappers`); граф — только наших платформ (ADR-60). `cargo vet`: импорт аудитов, доверие издателям, которым доверяют Mozilla/ISRG/Bytecode Alliance или уже доверяет проект, остальное — исключения «аудит не проведён» (ADR-55) |

## Ключ личности устройства (пункт 4)
`sm_signal::identity::DeviceIdentity`: `IdentityKeyPair` из libsignal (`OsRng`) и номер регистрации (14 бит, не ноль). Секрет: `[версия 1][номер регистрации u32 BE][IdentityKeyPair::serialize()]`; при разборе открытый ключ должен получаться из закрытого — иначе отказ. Хранение — `sm_core::keystore` под меткой `identity`, обёртка — платформа (`sm-ffi`: `PlatformKeyWrapper`, `PlatformKeyStorage`; объект `DeviceIdentity` с `load`/`create`, наружу — только открытый ключ 33 байта и номер регистрации). `create` никогда не перезаписывает запись: если она есть (даже повреждённая) — `Exists`.

## Метки поиска BLE (ADR-61, ADR-62)
`sm_signal::beacon`: метка 16 байт = первые 16 байт HMAC-SHA256(ключ, домен ‖ эпоха u64 BE), эпоха — 15 минут по времени Unix; HMAC — `CryptographicMac` из `signal-crypto` (тот же репозиторий и коммит libsignal; в графе уже был как зависимость `libsignal-protocol`). Домены: `sm-ble/v1` (ключ маяка контакта, 32 байта), `sm-pair/v1` (секрет из QR, 16 байт), `sm-add/v1` (экран «Добавить рядом», открытый ключ). `contact_tokens_around` — эпохи t−1, t, t+1. `pairing_proof`/`pairing_proof_ok` — HMAC набора ключей секретом из QR, сравнение без раннего выхода. Тест — известный ответ RFC 4231. В `sm-ffi`: `ble_epoch_ms`, `ble_add_nearby_token`, `ble_pairing_token`, `ble_contact_token`, `ble_contact_tokens_around`, `beacon_key_new`, `pairing_secret_new`.


## ID своей очереди на узле (ADR-134)
`sm_signal::queue` (#67): ID получателя = HMAC-SHA256(секрет очередей устройства, `sm-queue/v1` ‖ адрес контакта ‖ номер периода u64 BE); HMAC — `CryptographicMac` из `signal-crypto`, как у меток BLE. Секрет — 32 байта из `OsRng`, контактам не передаётся. Тест — известный ответ (посчитан в Python `hmac`). В `sm-ffi`: `queue_secret_new`, `queue_recipient_id` (пустой адрес или секрет не 32 байта — `BadInput`).

## Шифрование частей BLE (ADR-92)
`sm_signal::ble_part`: каждая часть `sm_core::chunk` уходит в эфир как `nonce 12 случайных байт ‖ AES-256-GCM(ключ части, nonce, связанные данные `sm-ble-part/v1`, открытая часть) ‖ метка 16` — снаружи нет версии, номеров, длин и постоянных полей. Ключ части = HMAC-SHA256(секрет, домен): контакту — ключ маяка **получателя** (`sm-ble-part/v1/contact`; получатель открывает своим ключом без перебора), сопряжение по QR — секрет из QR (`sm-ble-part/v1/pair`), «Добавить рядом» — открытый секрет (`sm-ble-part/v1/add`; прячет только формат). Примитивы — `Aes256GcmEncryption`/`Decryption` и `CryptographicMac` из `signal-crypto`, своей криптографии нет. Случайный nonce 96 бит — не больше 2³² частей на ключ (NIST SP 800-38D, п. 8.3). Тест-различитель: 10 000 частей неотличимы от случайных по частотам байтов. В `sm-ffi`: `ble_parts_seal`, `ChunkReassembler(ключ части)` (ошибки `NotOpened`, `BadKey`), `chunk_min_len`, `ble_part_key_contact`, `ble_part_key_pairing`, `ble_part_key_nearby`.
## Хранилища libsignal (ADR-63 п.3)
`sm_signal::store`: трейт `Kv` (get/put/delete по таблице и id) — его даёт платформа; поверх него ядро реализует `IdentityKeyStore`, `SessionStore`, `PreKeyStore`, `SignedPreKeyStore`, `KyberPreKeyStore` (трейты libsignal — через `async-trait` 0.1.92, та же версия, что в графе libsignal). Таблицы: `signal_identity`, `signal_session` (id — `адрес.устройство`), `signal_prekey`, `signal_signed_prekey`, `signal_kyber_prekey` (id — номер u32 BE). Значения — сериализация самой libsignal; шифрование строк ключом `sm.store` (связанные данные `sm/v1/` + таблица + id) — на стороне платформы. Свой ключ личности в базе не хранится — его даёт `DeviceIdentity`. Доверие ключу контакта: записанный для адреса — только он; адреса без записи — первое знакомство, а адрес = ключ личности в hex, так что «сменить ключ» у адреса нельзя. Ключ Kyber одноразовый: `mark_kyber_pre_key_used` удаляет его — повтор сообщения начала сессии получает отказ. Ошибка `Kv` — отказ операции (ADR-63 п.5). `MemKv` — в памяти, для тестов и самопроверки.

## Контакт и сессия (ADR-62, пункты 5–6)
`sm_signal::contact`:
- **карточка** (`new_card`) — свежий набор ключей на одно добавление: ключ личности, номер регистрации, одноразовый, подписанный и Kyber1024 (номера — 24 бита, `OsRng`); закрытые половины — в хранилище. Формат: `[версия 1][рег. u32][ключ личности][id][одноразовый][id][подписанный][подпись][id][Kyber][подпись]`, ключи и подписи с длиной u16 BE, строгий разбор (лишние байты — отказ); ≈ 1,8 КБ;
- `start_session` — PQXDH по карточке (подписи проверяет libsignal) и первое сообщение; своя карточка — отказ;
- `accept_session(…, expected_identity)` — сообщение начала сессии; ключ личности отправителя не тот, что в QR — отказ **до** расшифровки, в хранилище ничего не пишется;
- `encrypt`/`decrypt` — `[тип 3|2][сообщение libsignal]`; сообщение начала сессии от другого ключа, чем у контакта, — отказ; `forget` — удалить сессию и ключ контакта;
- `decrypt_from_any(кандидаты, кадр)` — отправитель кадра Bluetooth не подписан (сервер GATT не знает, кто записал): сообщение начала сессии пробуется только у контакта с его ключом личности, обычное — по очереди с сессией каждого кандидата; libsignal сначала проверяет MAC и при неудаче ничего не сохраняет, так что чужие сессии не портятся (тест). Никто не подошёл (не контакт, подделка, повтор того же шифротекста) — `None`; сбой хранилища — ошибка;
- `Hello` — первое сообщение: `[версия 1][ключ маяка 32][имя UTF-8 ≤ 128 байт]`; ключ маяка и имя идут только внутри Signal (ADR-61 п.2), в `Debug` ключа нет;
- `safety_number` — код безопасности 60 цифр (`Fingerprint` libsignal, версия 2, 5200 итераций, идентификатор — ключ личности), одинаковый на обоих телефонах.

`sm_signal::pairing`: QR — строка `SM1:` + HEX(ключ личности 33 ‖ секрет 16), заглавные (буквенно-цифровой режим QR), ключ должен разбираться как ключ libsignal. Кадры по Bluetooth на экране добавления (`PairFrame`, ≤ 8 КБ): `Card` (`[1][длина u16][карточка][доказательство 0|32]`), `Start` (`[2][сообщение]`), `Reply` (`[3][сообщение]`), `Decline` (`[4]`), `Intro` (`[5][имя UTF-8 ≤ 128 байт]` — имя для списка «Добавить рядом», UX-25: видно телефонам с открытым тем же экраном).

Сценарий QR: А показывает QR → Б сканирует и шлёт `Card` с доказательством (HMAC карточки секретом QR) → А проверяет доказательство своим секретом, `start_session` со своим `Hello` → `Start` → Б `accept_session` с ключом из QR, отвечает своим `Hello` → `Reply` → А расшифровывает. Оба — «сверен». «Добавить рядом» — то же без доказательства и без ключа из QR, после подтверждения пользователем; оба — «не сверен».

`sm-ffi` (`signal.rs`): `PlatformKv` (обратный вызов Kotlin, таблица — строкой), объект `SignalSessions` (`card_frame`, `accept_card`, `accept_start`, `reply_frame`, `open_reply`, `encrypt`, `decrypt`, `forget`; все вызовы — по очереди под замком, libsignal переписывает сессию), функции `qr_encode`/`qr_decode`, `pair_frame_decode`, `pair_frame_decline`, `pair_frame_intro`, `safety_number`. Ошибки: `BadInput`, `Mismatch`, `Protocol`, `Store` (в т.ч. сбой хранилища внутри libsignal), `Callback`.

## Сообщения 1:1 (пункт 6)
`sm-ffi` (`chat.rs`): `message_id_new` (16 байт `OsRng`), `chat_encode(ChatMessage)` — `Text` или `Delivered` в формате `sm_core::message`, затем `padding::pad`; `contact_mailbox(адрес)` — ящик контакта для `OutboxQueue` и `SeenWindow`: ключ личности без байта типа (32 байта); `SignalSessions.open(кандидаты, кадр)` — `decrypt_from_any` → `unpad` → разбор; ответ, реакция и неизвестные типы — `Other { kind }` (подтверждаются, но пока не показываются). Расшифровалось, но не сообщение — `BadInput` (сессия уже сдвинулась; ошибка отправителя).

В очереди лежит **открытое** выровненное сообщение (на диске — под `sm.store`, ADR-56), шифруется оно на каждой попытке отправки: libsignal отвергает повтор того же шифротекста, и при потерянном подтверждении сообщение осталось бы недоставленным навсегда. Новый шифротекст получатель расшифрует, дубль отсечёт `SeenWindow` по id и подтвердит снова (ADR-40). Подтверждение `Delivered` в очередь не ставится: потерялось — отправитель повторит сообщение, получатель подтвердит ещё раз.
