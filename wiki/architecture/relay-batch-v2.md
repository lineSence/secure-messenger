# Wire v2: ограниченные пакетные команды

Статус: реализация добавлена отдельным пакетом поверх wire v1; не является расширением версии 1. Поручение владельца — реализовать batch вместе с масштабированием (чат 2026-10-14). Спецификация соответствует `sm-core::relay_batch`, интеграционным тестам `sm-relay/tests/batch.rs`; отправка из Kotlin пока не подключена.

## Конверт

- Транспорт — прежние TCP-кадры или HTTP POST от reverse proxy. TLS, подписи и модель capability не меняются.
- Запрос: `[version=2 u8][command=10 u8][reserved ID=32 нулевых байта][length u32 BE][body]`.
- Body: `[count u8][полный кадр v1 первого элемента][полный кадр v1 второго элемента]...`. У каждого элемента свои command, ID, length и body; вложенные конверты запрещены.
- Count от 1 до 32; суммарное body не больше `MAX_BLOB` (131136 байт). Это конечная защита на один проход, а не увеличение предела отдельного блоба. Почти максимальный/максимальный SEND следует отправлять отдельной командой v1: внутри batch есть дополнительные заголовки.
- Разрешены только SEND, FETCH, ACK, DEL, PING. WAIT, NEW, TICKET, GUEST запрещены: пакет не занимает WAIT-слоты, не обходит выдачу пропусков/лимиты создания и не собирает большой пакет подписей.
- Ответ: `[version=2][outer status][length u32 BE][body]`. При корректном конверте body содержит `[count u8]`, затем для каждого элемента `[status u8][length u32 BE][data]` в исходном порядке. Статусы/data совпадают с v1, в том числе индекс FETCH и ACK u64 BE.
- Максимальный body ответа — `MAX_RESPONSE_DATA` (131145 байт). Под каждый оставшийся элемент резервируется хотя бы его пустой заголовок ответа. FETCH, результат которого не помещается, получает TooBig с пустыми данными; сообщение не удаляется, клиент повторяет отдельный FETCH. Предыдущие успешные элементы не откатываются.

## Семантика и ошибки

До первого изменения состояния валидируются **все** кадры пакета, допустимость команд, размеры и отсутствие хвоста. Неправильный поздний элемент даёт внешний BadRequest без выполнения ранних элементов; соединение закрывается. Неправильное внешнее framing может быть отвергнуто HTTP 400/закрытием либо ответом BadRequest старого формата, как при неизвестной версии.

Корректный пакет выполняется последовательно, **не транзакционно**. Ошибка одного элемента не отменяет успешные предыдущие и не запрещает следующие. Внешний OK означает «пакет разобран и обработан», а не «все элементы успешны»: проверять каждый status. Квоты остаются общими между шардами и между v1/v2.

Потеря ответа может произойти после выполнения части или всего корректного пакета. Повтор SEND допускает дубликат, ACK остаётся идемпотентным, DEL может повторно дать NoQueue. Exactly-once/атомарность пакета не обещаются; дедупликация сообщений — клиентская, как в v1.

## Совместимость и внедрение

Wire v1 parser по-прежнему отвергает version=2; его команда/длина/ответы не расширены скрыто. Новый сервер обслуживает v1 и v2 на том же listener. Старый клиент продолжает v1 без обновления; Kotlin и FFI этим пакетом не переключены.

Проверка поддержки возможна отдельным **неизменяющим состояние** v2-пакетом с одним PING. Старый узел отвергнет конверт и может закрыть соединение; после повторного соединения клиент продолжает v1. Нельзя проверять поддержку первым реальным пакетом SEND и, потеряв ответ, молча переисполнять его как v1 без модели повторов.

Эталонный codec клиента — `sm_core::relay_batch::{encode_request,decode_response}`. Golden, malformed/trailing/truncation и round-trip тесты — в модуле; обработка узла — в интеграционных тестах; недоверенный codec — отдельная цель fuzz `relay_batch`.

HA этим протоколом не реализуется: успешный SEND текущего standalone-узла всё ещё подтверждает RAM одного процесса. Кворумный режим ADR-153 требует отдельной реализации согласования.
