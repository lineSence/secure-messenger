# Узел-реле `sm-relay` (шаг 2 плана MVP)

Статус: **принято** владельцем 2026-10-09 (ответы на вопросы — в конце). Решения: ADR-8, ADR-9, ADR-12. Факты о хостинге — `wiki/references/server-hosting.md`.

## Что делает
Один зарубежный узел хранит зашифрованные блобы в очередях до получения. Содержимое узел не читает: шифруют клиенты (libsignal/OpenMLS, шаг 3). Узел — отдельный бинарник `crates/sm-relay` в том же workspace, разбор запросов — через `sm-core::wire`.

## Очереди
- Очередь однонаправленная. У неё два случайных ID по 32 байта: ID отправителя (им кладут) и ID получателя (им забирают). Узнав одно, нельзя связать его с другим без памяти узла. Так же устроены очереди SimpleX: «different IDs for sender and recipient… to prevent the correlation of senders and recipients commands» ([simplex-messaging.md](https://github.com/simplex-chat/simplexmq/blob/stable/protocol/simplex-messaging.md), на 2026-10-09).
- ID — права доступа: кто знает ID получателя, тот читает очередь. Своей криптографии нет (ADR-1): ID — случайные байты из ОС, канал защищает транспорт (шаг 4).
- Команды (код): `NEW` (1) → (ID получателя, ID отправителя); `SEND` (2, ID отправителя, блоб); `FETCH` (3, ID получателя) → номер u64 BE + самый старый блоб или `EMPTY`; `ACK` (4, ID получателя, номер u64 BE) → блоб удалён, повтор безопасен; `DEL` (5, ID получателя) → очередь удалена; `PING` (6) — проба для диагностики (ADR-13); `WAIT` (7, ID получателя) — как `FETCH`, но при пустой очереди узел ждёт блоб до 25 с, `SEND` в ту же очередь будит его сразу (ADR-82).
- Коды ответа: 0 `OK`, 1 `EMPTY`, 2 `NO_QUEUE`, 3 `TOO_BIG`, 4 `QUOTA`, 5 `BAD_REQUEST` (соединение закрывается), 6 `UNAVAILABLE`.
- Блоб удаляется после `ACK`. Если `ACK` не пришёл (обрыв связи), `FETCH` вернёт тот же блоб снова — сообщение не теряется.

## Только RAM, TTL, без логов
- Всё состояние — в памяти процесса; на диск ничего не пишется. Рестарт стирает все очереди (критерий шага 2).
- TTL блоба — 7 дней (`overview.md`); очередь без обращений 30 дней удаляется. Время поступления хранится с точностью до часа.
- Логов нет: ни IP, ни ID очередей, ни размеров. В stdout — только ошибка запуска. systemd: `StandardOutput=null`, `LimitCORE=0` (core-дамп сохранил бы память с очередями на диск).
- На сервере выключен swap: иначе ядро может выгрузить блобы на диск. Ту же защиту дают `mlock()/mlockall()`, но в Linux это привилегированный вызов ([Secure Programs HOWTO, 11.4](https://tldp.org/HOWTO/Secure-Programs-HOWTO/protect-secrets.html), на 2026-10-09), поэтому выбран выключенный swap.

## Пределы (враждебный клиент)
| Что | Предел | Ответ при превышении |
|---|---|---|
| Блоб | 128 КиБ + 64 байта (максимум `padding`) | `TOO_BIG` |
| Блобов в очереди | 1000 | `QUOTA` |
| Байт в одной очереди | 32 МиБ | `QUOTA` |
| Новых очередей за час (на весь узел) | 100 | `QUOTA` |
| Очередей | 10 000 | `QUOTA` |
| Вся память блобов | 256 МиБ | `QUOTA` |
| Весь кадр запроса (с начала ожидания) и отправка ответа | 30 с | соединение закрыто |
| Одновременных соединений | 64 | лишние закрываются сразу |
Память под блоб выделяется только после проверки длины по этим пределам. Срок 30 с — на кадр целиком, а не на каждое чтение: клиент, присылающий по байту раз в 29 с, не держит слот соединения (находка ревью PR #8).

Остаточный риск: кто достучался до порта, может занять пределы узла (очереди, 64 соединения) — пределы общие, а не на клиента, потому что через SSH-туннель все приходят с `127.0.0.1`. Сейчас доступ закрыт SSH; на шаге 4 его ограничит VLESS + Reality (подключиться могут только наши клиенты).

## Сеть на шаге 2
- Узел слушает только `127.0.0.1`. Клиенты шага 2 (тестовые) ходят через SSH-туннель; на шаге 4 перед узлом встанет VLESS + XHTTP + Reality (ADR-7). Уточнение 2026-10-11: в 0.0.2-alpha перед узлом — nginx с HTTPS на своём домене (ADR-84, принято; схема — ADR-90, предложено), VLESS + XHTTP + Reality — в 0.0.3-alpha. TLS-библиотека на шаге 2 не нужна.
- Кадр: `[версия u8 = 1][команда u8][ID 32 байта][длина u32 BE][данные]`. Ответ: `[версия][код u8][длина u32 BE][данные]`.
- Протокол и плагин `RelayTcp` (интерфейс `Transport`: `send`, `fetch`, `probe`, плюс `create_queue`, `delete_queue`) — `sm-core::relay`; узел и клиент используют один разбор кадров. `RelayTcp::fetch` подтверждает (`ACK`) каждый полученный блоб; при обрыве посреди вызова возвращает уже полученные блобы, а не ошибку (иначе подтверждённые блобы терялись бы — находка ревью PR #8). Если `ACK` не дошёл, блоб придёт снова: доставка «хотя бы раз», повторы клиент отбрасывает по ID сообщения (шаг 3). Соединение, простоявшее больше 20 с, клиент не переиспользует (узел закрывает простаивающие через 30 с); если узел всё же закрыл соединение, клиент один раз переподключается и повторяет запрос — закрытие по простою не выдаётся за блокировку (находка ревью PR #8).
- Адрес узла — переменная `SM_RELAY_LISTEN` (по умолчанию `127.0.0.1:7400`); не loopback-адрес узел отвергает при запуске. Юнит systemd — `crates/sm-relay/deploy/sm-relay.service` (`DynamicUser`, `PrivateDevices`, `SystemCallFilter=@system-service`, без capabilities, сеть только localhost).

## Приём HTTP/1.1 от nginx (0.0.2-alpha, ADR-90)
- Режим — `SM_RELAY_MODE=http` (иначе `tcp`: кадры прямо по TCP). Узел по-прежнему слушает только `127.0.0.1`; снаружи HTTPS держит nginx и проксирует секретный путь на узел.
- Узкое подмножество (`crates/sm-relay/src/http.rs`): только `POST / HTTP/1.1`, тело — ровно один кадр с `Content-Length` (не больше заголовка кадра + 128 КиБ + 64 байта), без `Transfer-Encoding` и продолжения строк, заголовок до 2048 байт и до 32 полей. Ответ — `200` с одним кадром в теле, `Cache-Control: no-store`. Всё остальное — `400` и закрытие соединения.
- Соединение переиспользуется (keepalive nginx к узлу), пока в `Connection` нет `close`.
- `WAIT` ждёт до 25 с — меньше 30 с `proxy_read_timeout` nginx.

## Зависимости
Только `std` и `sm-core` (поток на соединение; пользователей 2–5). Случайные ID — 32 байта из `/dev/urandom` (узел работает только на Linux), поэтому `getrandom` не понадобился. Асинхронный рантайм на шаге 2 не нужен.

## Проверки (CI)
- Юнит-тесты очередей: TTL, `ACK`, пределы, повтор `FETCH` без `ACK`.
- Интеграционный тест (`crates/sm-relay/tests/two_clients.rs`): два клиента через `127.0.0.1` обмениваются блобами; после остановки и нового запуска сервера на том же порту очередей нет. Перезапуск — внутри тестового процесса: запуск бинарника из теста запретило бы правило semgrep `sm-no-process-spawn`, а состояние и так живёт только в памяти `Server`.
- Фаззинг разбора кадра (`fuzz/fuzz_targets/relay_frame.rs`), Kani — разбор кадра без паник.
- HTTP: юнит-тесты разбора, фаззер `relay_http`; Kani (`cargo kani -p sm-relay -Z stubbing`, `crates/sm-relay/src/proofs.rs`, только к релизу — ADR-105) — по частям: `http_head_total` (20 байт, строка поля, имя, `Content-Length` и `Connection` — заглушки с тем же контрактом), `http_field_total` (24 байта), `http_kind_total` (24), `http_length_total` (12, длина не больше предела), `http_close_total` (10), `http_head_end_total` (12).
- Semgrep `sm-relay-no-logs` (`.semgrep/relay.yml`): запрет `println!`/`eprintln!`/`dbg!`/`log`/`tracing` в `crates/sm-relay`.

## Хостинг и деньги
Предел — $10/мес (R-15). К конкретному провайдеру не привязываемся (решение владельца 2026-10-09). Требования к VPS: не санкционный провайдер (ADR-9), Linux, 1 vCPU и от 1 ГиБ RAM (256 МиБ под блобы + система), можно выключить swap, 1 IPv4. Узел ставится одним бинарником и юнитом systemd, поэтому переезд к другому провайдеру — минуты.

## Решения владельца (2026-10-09)
1. После рестарта узла клиент сам заново создаёт очередь; новые ID передаются контактам через запасной путь (шаг 5). До шага 5 после рестарта контакты заново обмениваются ссылками.
2. Шаг 2 — только `127.0.0.1` + SSH-туннель, без открытого порта до шага 4.
3. Провайдер не фиксируется: подойдёт любой, кто выполняет требования выше.
