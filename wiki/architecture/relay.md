# Узел-реле `sm-relay` (шаг 2 плана MVP)

Статус: **принято** владельцем 2026-10-09 (ответы на вопросы — в конце). Решения: ADR-8, ADR-9, ADR-12. Факты о хостинге — `wiki/references/server-hosting.md`.

## Принятое уточнение контракта и масштаба
ADR-152 / R-23 (владелец, 2026-10-14): `wiki/architecture/relay-contract.md` — фиксируем внешний контракт, не реализацию. RAM-only и полный запрет телеметрии остаются. Малое число пользователей, бюджетный VPS и единственный узел больше не ограничивают архитектуру. Числа ниже описывают **текущую реализацию**, не вечные константы контракта. Конфигурируемые квоты и масштабирование согласованы как направление, но пока не реализованы; wire v1 не изменён.

## Что делает
Один зарубежный узел хранит зашифрованные блобы в очередях до получения. Содержимое узел не читает: шифруют клиенты (libsignal/OpenMLS, шаг 3). Узел — отдельный бинарник `crates/sm-relay` в том же workspace, разбор запросов — через `sm-core::wire`.

## Очереди
- Очередь однонаправленная. У неё два ID по 32 байта: ID получателя (им забирают) — случайный, его выбирает клиент; ID отправителя (им кладут) = SHA-256(`sm-qsend/v1` ‖ ID получателя), считает узел (ADR-134). По ID отправителя ID получателя не узнать — нужен прообраз SHA-256. Так же устроены очереди SimpleX: «different IDs for sender and recipient… to prevent the correlation of senders and recipients commands» ([simplex-messaging.md](https://github.com/simplex-chat/simplexmq/blob/stable/protocol/simplex-messaging.md), на 2026-10-09).
- ID — права доступа: кто знает ID получателя, тот читает очередь. Своей криптографии нет (ADR-1): ID получателя — случайные байты из ОС, SHA-256 — через `signal-crypto` (libsignal), канал защищает транспорт (шаг 4).
- Команды (код): `NEW` (1, ID получателя; в данных — пропуск 91 байт) → ID отправителя; повтор на живую очередь — тот же ответ без изменений, поэтому `NEW` можно повторять (ADR-134); `SEND` (2, ID отправителя, блоб); `FETCH` (3, ID получателя; в данных — ещё до 63 ID получателя, всего до 64 очередей, ADR-114) → самый старый блоб выбранной непустой очереди списка (FIFO внутри очереди, round-robin между очередями): номер очереди в списке u8 + номер блоба u64 BE + блоб, или `EMPTY`; `ACK` (4, ID получателя, непрозрачный номер u64 BE) → блоб удалён, повтор безопасен в том же экземпляре очереди; `DEL` (5, ID получателя) → очередь удалена; `PING` (6) — проба для диагностики (ADR-13); `WAIT` (7, список как у `FETCH`) — как `FETCH`, но если все очереди пусты, узел ждёт блоб до 25 с, `SEND` в любую из них будит его сразу; `DEL` тоже будит ожидание (ADR-82, ADR-114); `TICKET` (8, в данных пропуск владельца 91 байт или гостевой 107) → билет 32 байта (ADR-146); `GUEST` (9, билет в поле ID, данных нет) → гостевой пропуск 107 байт (ADR-146).
- Нет одной из очередей списка (узел перезапускался) — `NO_QUEUE`, в данных номер этой очереди в списке (u8): клиент делает `NEW` с тем же ID получателя — ID отправителя тот же, контакту ничего передавать не нужно (ADR-134).
- Коды ответа: 0 `OK`, 1 `EMPTY`, 2 `NO_QUEUE`, 3 `TOO_BIG`, 4 `QUOTA`, 5 `BAD_REQUEST` (соединение закрывается), 6 `UNAVAILABLE`, 7 `DENIED` (пропуск на `NEW` или `TICKET` не принят, билета нет или он истёк). `TICKET` и `GUEST` на узле без ключа гостевых пропусков — `UNAVAILABLE`.

## Пропуск на `NEW` (ADR-136)
- `NEW` узел выполняет только с пропуском, подписанным офлайн корневым ключом владельца (ADR-127). Формат (`sm-core::pass`, числа big-endian): `[версия 1][ID пропуска 16 байт][действует до u64, с][новых очередей в час u16 > 0][подпись XEdDSA 64 байта над `SM queue pass v1\0` ‖ первые 27 байт]`. Контекст подписи отличает пропуск от записи узла, подписанной тем же ключом.
- Узел проверяет подпись открытыми корневыми ключами (`ROOT_KEYS` в `sm-core::node`, проверка — `libsignal-core`) и срок; списка выданных пропусков не хранит. Отозванные — переменная `SM_RELAY_REVOKED` (ID через запятую, 32 HEX). Подпись не владельца, истёкший срок или отзыв — `DENIED`.
- Лимит новых очередей в час — свой у каждого пропуска (поле «в час»); общий предел узла 100/ч остаётся.
- Выпуск — `sm-node-tool pass` (текст `SMP1:` + HEX, `relay-deploy.md` §6); в приложении — FFI `queue_pass_open`, `HttpsRelay.newQueue(recipientId, pass)`.
## Билет и гостевой пропуск (ADR-146)
- Зачем: приглашённому по ссылке не нужен пропуск владельца. Пригласивший перед созданием ссылки просит у узла билет (`TICKET`, по своему пропуску — владельца или гостевому); билет лежит в ссылке (необязательные 32 байта в конце содержимого, `sm-signal::invite`). Принявший меняет билет (`GUEST`) на гостевой пропуск и дальше создаёт свои очереди сам: на каждый контакт раз в 30 дней и после перезапуска узла (ADR-137), поэтому билета «на пару очередей» мало — гостю нужен долговременный пропуск.
- Билет — 32 случайных байта (`OsRng`), только в памяти узла, живёт 25 часов (ссылка — 24), не больше 1000 штук; считается в лимит новых очередей выдавшего пропуска. Повторный `GUEST` с тем же билетом возвращает тот же пропуск (ответ мог потеряться по дороге).
- Гостевой пропуск (`sm-core::pass::GuestPass`, big-endian): `[версия 2][ID 16][до u64, с][в час u16 > 0][ID родительского пропуска 16][подпись XEdDSA 64 байта над `SM guest pass v1\0` ‖ первые 43 байта]` — 107 байт. Подписывает сам узел постоянным ключом (`libsignal-core`, своей криптографии нет, ADR-1): ключ — файл из 64 HEX-знаков, путь `SM_RELAY_GUEST_KEY_FILE` или `$CREDENTIALS_DIRECTORY/guest-key` (systemd `LoadCredential`); так пропуск переживает перезапуск узла. Без ключа узел билетов не выдаёт. Сменить ключ — отозвать всех гостей.
- Права гостя: не больше 10 новых очередей в час (`GUEST_PER_HOUR`) и не больше родительского лимита; срок — не дольше года и не дольше родительского пропуска. Родитель — пропуск владельца, от которого пошла цепочка (гость может приглашать дальше, родитель остаётся тот же). Пропуск владельца в `SM_RELAY_REVOKED` отзывает и всех гостей цепочки.
- Гостевой пропуск годится только на узле, который его выдал. `NEW` принимает пропуск владельца и гостевой (по длине). Приложение: FFI `guest_pass_open` (формат и срок; подпись проверяет узел), `HttpsRelay.ticket/guestPass`, `RelayAccount.setGuest`.
- Номер блоба — непрозрачные 8 байт: клиент возвращает полученное значение в ACK, не предполагает старт с нуля. При создании очереди используется случайный 63-битный старт из OsRng; дальше счётчик растёт без wraparound (при исчерпании — UNAVAILABLE без записи). Это совместимая вероятностная защита от запоздалого ACK прежнего экземпляра очереди, не математическая гарантия отсутствия коллизий между рестартами. Формат кадров и текущие клиенты не меняются.
- Обход списка FETCH/WAIT начинается после ранее обслуженной очереди. Курсор хранится в первой очереди списка, удаляется с ней и не создаёт неограниченный кеш произвольных списков. Для неизменного списка с одним получателем непрерывно заполненная первая очередь не голодает остальные.
- Пустой SEND — BAD_REQUEST и закрытие соединения: штатный Android-клиент не может обработать пустую голову.
- Блоб удаляется после `ACK`. Если `ACK` не пришёл (обрыв связи), `FETCH` вернёт тот же блоб снова — сообщение не теряется.

## Только RAM, TTL, без логов
- Всё состояние — в памяти процесса; на диск ничего не пишется. Рестарт стирает все очереди (критерий шага 2).
- TTL блоба — 7 дней (`overview.md`); очередь без обращений 30 дней удаляется. Время поступления хранится с точностью до часа.
- Логов нет: ни IP, ни ID очередей, ни размеров. В stdout — только ошибка запуска. systemd: `StandardOutput=null`, `LimitCORE=0` (core-дамп сохранил бы память с очередями на диск).
- На сервере выключен swap: иначе ядро может выгрузить блобы на диск. Ту же защиту дают `mlock()/mlockall()`, но в Linux это привилегированный вызов ([Secure Programs HOWTO, 11.4](https://tldp.org/HOWTO/Secure-Programs-HOWTO/protect-secrets.html), на 2026-10-09), поэтому выбран выключенный swap.

## Пределы (враждебный клиент)
| Что | Предел | Ответ при превышении |
|---|---|---|
| Блоб | 128 КиБ + 64 байта (максимум `padding`) | `TOO_BIG` |
| Блобов в очереди | 1000 | `QUOTA` |
| Байт в одной очереди | 32 МиБ | `QUOTA` |
| Новых очередей за час (на весь узел) | 100 | `QUOTA` |
| Новых очередей за час (на пропуск) | поле пропуска | `QUOTA` |
| Очередей | 10 000 | `QUOTA` |
| Вся память блобов | 256 МиБ | `QUOTA` |
| Весь кадр запроса (с начала ожидания) и отправка ответа | 30 с | соединение закрыто |
| Одновременных соединений | 64 | лишние закрываются сразу |
| Припаркованных WAIT | 48 из 64 (четверть соединений — резерв) | UNAVAILABLE и закрытие соединения; SEND/ACK/NEW/PING не занимают бюджет WAIT |
При WAIT пустой очереди socket проверяется неблокирующим peek с шагом до 100 мс, без mutex хранилища; видимый EOF/сброс отменяет ожидание, освобождая бюджет. FIN трактуется как отмена WAIT: клиент не должен делать shutdown(write), если продолжает ждать long-poll ответ. Если в сокете остаются непрочитанные pipelined bytes, EOF может быть виден позже; общий предел WAIT всё равно оставляет резерв. DEL уведомляет Condvar и возвращает NO_QUEUE без ожидания 25 с. Резерв защищает от насыщения именно WAIT, но не гарантирует доступность при заполнении всех 64 слотов медленными/idle соединениями; защита внешнего прокси остаётся отдельной задачей.

Память под блоб выделяется только после проверки длины по этим пределам. Срок 30 с — на кадр целиком, а не на каждое чтение: клиент, присылающий по байту раз в 29 с, не держит слот соединения (находка ревью PR #8).

Остаточный риск: кто достучался до порта, может занять пределы узла (очереди, 64 соединения) — пределы общие, а не на клиента, потому что через SSH-туннель все приходят с `127.0.0.1`. Решение — `NEW` только с пропуском, лимит на пропуск (ADR-136, сделано в #65). Сейчас доступ закрыт SSH; на шаге 4 его ограничит VLESS + Reality (подключиться могут только наши клиенты).

## Сеть на шаге 2
- Узел слушает только `127.0.0.1`. Клиенты шага 2 (тестовые) ходят через SSH-туннель; на шаге 4 перед узлом встанет VLESS + XHTTP + Reality (ADR-7). Уточнение 2026-10-11: в 0.0.2-alpha перед узлом — nginx с HTTPS на своём домене (ADR-84, принято; схема — ADR-90, предложено), VLESS + XHTTP + Reality — в 0.0.3-alpha. TLS-библиотека на шаге 2 не нужна.
- Кадр: `[версия u8 = 1][команда u8][ID 32 байта][длина u32 BE][данные]`. Ответ: `[версия][код u8][длина u32 BE][данные]`.
- Протокол и плагин `RelayTcp` (интерфейс `Transport`: `send`, `fetch`, `probe`, плюс `create_queue`, `delete_queue`) — `sm-core::relay`; узел и клиент используют один разбор кадров. `RelayTcp::fetch` подтверждает (`ACK`) каждый полученный блоб; при обрыве посреди вызова возвращает уже полученные блобы, а не ошибку (иначе подтверждённые блобы терялись бы — находка ревью PR #8). Если `ACK` не дошёл, блоб придёт снова: доставка «хотя бы раз», повторы клиент отбрасывает по ID сообщения (шаг 3). Соединение, простоявшее больше 20 с, клиент не переиспользует (узел закрывает простаивающие через 30 с); если узел всё же закрыл соединение, клиент один раз переподключается и повторяет запрос — закрытие по простою не выдаётся за блокировку (находка ревью PR #8).
- Адрес узла — переменная `SM_RELAY_LISTEN` (по умолчанию `127.0.0.1:7400`); не loopback-адрес узел отвергает при запуске. Юнит systemd — `crates/sm-relay/deploy/sm-relay.service` (`DynamicUser`, `PrivateDevices`, `SystemCallFilter=@system-service`, без capabilities, сеть только localhost).

## Приём HTTP/1.1 от nginx (0.0.2-alpha, ADR-90)
- Режим — `SM_RELAY_MODE=http` (иначе `tcp`: кадры прямо по TCP). Узел по-прежнему слушает только `127.0.0.1`; снаружи HTTPS держит nginx и проксирует секретный путь на узел.
- Узкое подмножество (`crates/sm-relay/src/http.rs`): только `POST / HTTP/1.1`, тело — ровно один кадр с `Content-Length` (не больше заголовка кадра + 128 КиБ + 64 байта), без `Transfer-Encoding` и продолжения строк, заголовок до 2048 байт и до 32 полей. Ответ — `200` с одним кадром в теле, `Cache-Control: no-store`. Всё остальное — `400` и закрытие соединения.
- Соединение переиспользуется (keepalive nginx к узлу), пока в `Connection` нет `close`.
- `WAIT` ждёт до 25 с — меньше 30 с `proxy_read_timeout` nginx.

## Зависимости
`std`, `sm-core`, `libsignal-core`, `signal-crypto` и `rand` (поток на соединение; пользователей 2–5). Случайные ID — 32 байта из `/dev/urandom` (узел работает только на Linux), поэтому `getrandom` не понадобился. Асинхронный рантайм на шаге 2 не нужен.

## Проверки (CI)
- Юнит-тесты очередей: TTL, `ACK`, пределы, повтор `FETCH` без `ACK`; `WAIT`/`FETCH` по списку очередей и `NO_QUEUE` с номером (`tests/http.rs`).
- Интеграционный тест (`crates/sm-relay/tests/two_clients.rs`): два клиента через `127.0.0.1` обмениваются блобами; после остановки и нового запуска сервера на том же порту очередей нет. Перезапуск — внутри тестового процесса: запуск бинарника из теста запретило бы правило semgrep `sm-no-process-spawn`, а состояние и так живёт только в памяти `Server`.
- Фаззинг разбора кадра (`fuzz/fuzz_targets/relay_frame.rs`), Kani — разбор кадра без паник.
- HTTP: юнит-тесты разбора, фаззер `relay_http`; Kani (`cargo kani -p sm-relay -Z stubbing`, `crates/sm-relay/src/proofs.rs`, только к релизу — ADR-132) — по частям: `http_head_total` (20 байт, строка поля, имя, `Content-Length` и `Connection` — заглушки с тем же контрактом), `http_field_total` (24 байта), `http_kind_total` (24), `http_length_total` (12, длина не больше предела), `http_close_total` (10), `http_head_end_total` (12).
- Semgrep `sm-relay-no-logs` (`.semgrep/relay.yml`): запрет `println!`/`eprintln!`/`dbg!`/`log`/`tracing` в `crates/sm-relay`.

## Хостинг и деньги
Исходный бюджет — $10/мес (R-15); ADR-152 снимает его как архитектурный потолок масштаба, не выбирая новые расходы. К конкретному провайдеру не привязываемся (решение владельца 2026-10-09). Исходный профиль VPS (не верхний предел): не санкционный провайдер (ADR-9), Linux, 1 vCPU и от 1 ГиБ RAM (256 МиБ под блобы + система), можно выключить swap, 1 IPv4. Узел ставится одним бинарником и юнитом systemd, поэтому переезд к другому провайдеру — минуты.

## Решения владельца (2026-10-09)
1. После рестарта узла клиент сам заново создаёт очередь (с #65, 2026-10-11 — с тем же ID получателя, ADR-134; пункт ниже про новые ID и ссылки устарел); новые ID передаются контактам через запасной путь (шаг 5). До шага 5 после рестарта контакты заново обмениваются ссылками.
2. Шаг 2 — только `127.0.0.1` + SSH-туннель, без открытого порта до шага 4.
3. Провайдер не фиксируется: подойдёт любой, кто выполняет требования выше.

## Совместимый пакет оптимизаций (в разработке)
Ветка perf/relay-bounded-wake: wire v1 без изменений. Сервер отправляет неизменяемый разделяемый блоб через vectored I/O без промежуточных полных копий, уведомляет WAIT по ID получателя, индексирует ближайшие сроки очередей (один таймер на очередь), освобождает пустую ёмкость VecDeque; подпись первого GUEST вынесена из общего lock. Бюджет общего числа сообщений — 100 000 по умолчанию, настраиваемый; это дополнительная ресурсная квота, не полный счётчик RSS. Server::stop закрывает соединения с ожиданием до 5 с; обработчик SIGTERM этим не добавлен.

Приоритеты и незавершённые части — `wiki/audits/2026-10-15-relay-optimization/implementation.md`. Поток на соединение, общий mutex, 100-мс проверка отмены сокета, массовая обработка одновременно истёкших объектов и wire v1 остаются; не объявлять все 18 находок закрытыми.
