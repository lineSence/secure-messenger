# Узел-реле `sm-relay` (шаг 2 плана MVP)

Статус: **предложено** (2026-10-09), ждёт ответа владельца на вопросы в конце. Решения: ADR-8, ADR-9, ADR-12. Факты о хостинге — `wiki/references/server-hosting.md`.

## Что делает
Один зарубежный узел хранит зашифрованные блобы в очередях до получения. Содержимое узел не читает: шифруют клиенты (libsignal/OpenMLS, шаг 3). Узел — отдельный бинарник `crates/sm-relay` в том же workspace, разбор запросов — через `sm-core::wire`.

## Очереди
- Очередь однонаправленная. У неё два случайных ID по 32 байта: ID отправителя (им кладут) и ID получателя (им забирают). Узнав одно, нельзя связать его с другим без памяти узла. Так же устроены очереди SimpleX: «different IDs for sender and recipient… to prevent the correlation of senders and recipients commands» ([simplex-messaging.md](https://github.com/simplex-chat/simplexmq/blob/stable/protocol/simplex-messaging.md), на 2026-10-09).
- ID — права доступа: кто знает ID получателя, тот читает очередь. Своей криптографии нет (ADR-1): ID — случайные байты из ОС, канал защищает транспорт (шаг 4).
- Команды: `NEW` → (ID получателя, ID отправителя); `SEND` (ID отправителя, блоб); `FETCH` (ID получателя) → самый старый блоб и его номер; `ACK` (ID получателя, номер) → блоб удалён; `DEL` (ID получателя) → очередь удалена.
- Блоб удаляется после `ACK`. Если `ACK` не пришёл (обрыв связи), `FETCH` вернёт тот же блоб снова — сообщение не теряется.

## Только RAM, TTL, без логов
- Всё состояние — в памяти процесса; на диск ничего не пишется. Рестарт стирает все очереди (критерий шага 2).
- TTL блоба — 7 дней (`overview.md`); очередь без обращений 30 дней удаляется. Время поступления хранится с точностью до часа.
- Логов нет: ни IP, ни ID очередей, ни размеров. В stdout — только ошибка запуска. systemd: `StandardOutput=null`, `LimitCORE=0` (core-дамп сохранил бы память с очередями на диск).
- На сервере выключен swap: иначе ядро может выгрузить блобы на диск. Ту же защиту дают `mlock()/mlockall()`, но в Linux это привилегированный вызов ([Secure Programs HOWTO, 11.4](https://tldp.org/HOWTO/Secure-Programs-HOWTO/protect-secrets.html), на 2026-10-09), поэтому выбран выключенный swap.

## Пределы (враждебный клиент)
| Что | Предел | Ответ при превышении |
|---|---|---|
| Блоб | 128 КиБ + 64 байта (максимум `padding`) | `TOO_BIG` |
| Блобов в очереди | 1000 | `QUOTA` |
| Очередей | 10 000 | `QUOTA` |
| Вся память блобов | 256 МиБ | `QUOTA` |
| Запрос без данных | 30 с | соединение закрыто |
Память под блоб выделяется только после проверки длины по этим пределам.

## Сеть на шаге 2
- Узел слушает только `127.0.0.1`. Клиенты шага 2 (тестовые) ходят через SSH-туннель; на шаге 4 перед узлом встанет VLESS + XHTTP + Reality (ADR-7). TLS-библиотека на шаге 2 не нужна.
- Кадр: `[версия u8 = 1][команда u8][ID 32 байта][длина u32 BE][данные]`. Ответ: `[версия][код u8][длина u32 BE][данные]`.
- В `sm-core` — плагин `RelayTcp` с интерфейсом `Transport` (`send`, `fetch`, `probe`).

## Зависимости
Цель — только `std` (поток на соединение; пользователей 2–5) и `getrandom` для ID, если его пропустят `cargo deny` и `cargo vet`. Асинхронный рантайм на шаге 2 не нужен.

## Проверки (CI)
- Юнит-тесты очередей: TTL, `ACK`, пределы, повтор `FETCH` без `ACK`.
- Интеграционный тест: два клиента через `127.0.0.1` обмениваются блобами; после перезапуска процесса очередей нет.
- Фаззинг разбора кадра (`fuzz/fuzz_targets/relay_frame.rs`), Kani — разбор кадра без паник.
- Semgrep: запрет `println!`/`log`/`tracing` в `crates/sm-relay` (вместо правила о логах).

## Хостинг и деньги
Предел — $10/мес (R-15). Пример под этот предел: Hetzner CX33 — $9.99/мес, CX23 — $6.49/мес без IPv4, цены с 2026-06-15 ([Hetzner Docs](https://docs.hetzner.com/general/infrastructure-and-availability/price-adjustment/), на 2026-10-09). Провайдера выбирает владелец (ADR-9: не санкционный).

## Вопросы владельцу

2. Шаг 2 — только `127.0.0.1` + SSH-туннель, без открытого порта до шага 4. Подходит?
3. Провайдер узла: Hetzner (CX23/CX33) или другой?
