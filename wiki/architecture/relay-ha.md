# RAM-only HA узла: принятое требование и границы реализации

Статус: **требование принято владельцем, HA ещё не реализован**. ADR-153, продолжение ADR-152. Источник — ответ «Ок» в текущем чате на вопрос «подтверждать SEND только после сохранения в RAM большинства из трёх узлов, а при потере большинства отказывать в записи?». Дата решения — 2026-10-14 по контексту чата; часы лаборатории — 2026-10-15.

## Принято

- Группа репликации состоит из **трёх** участников. Успешный ответ на `SEND` разрешён только после фиксации операции протоколом согласования с хранением в **RAM не менее двух участников**.
- Без доступного большинства запись отклоняется/не получает успешного подтверждения. Изолированное меньшинство не становится независимым пишущим узлом.
- RAM-only и полный запрет телеметрии неизменны. Репликация не разрешает WAL, снимки на диске, очереди на диске, swap, core dump или журналы операций.
- Одновременная потеря состояния всех трёх участников может уничтожить очереди и сообщения. Восстановление опирается на клиентские повторы, а не на обещание сохранности на диске.

**Точная граница:** кворум 2/3 переносит одну потерю реплики, не произвольную череду перезапусков. Потеря RAM двух реплик, на которых находилась единственная подтверждённая копия, тоже может уничтожить подтверждённую запись. Наличие третьего процесса само по себе не гарантирует полноту его состояния. Нельзя объявлять «данные теряются только при одновременном отказе всех трёх».

## Обязательства реализации, до её приёмки

Это проверки безопасности выбранного режима, **не описание существующего кода**:

1. Настоящее согласование лидера и журнала в RAM: порядок операций, term/epoch, голосование, подтверждённый префикс, конфликтующие лидеры, тайм-ауты и потерянные ответы. «Отправили на два адреса» недостаточно.
2. Согласованное состояние включает не только блобы: создание очереди, непрозрачный ACK-номер, `ACK`, `DEL`, expiry и состояние билетов/гостевых пропусков не должны восстанавливать удалённые сообщения или расходиться между владельцами. Конкретный состав репликации квот и ограничения доступности чтения надо явно специфицировать.
3. Участник, потерявший RAM, стартует **неголосующей репликой**, а не прежним голосующим участником с обнулёнными term/vote. Возвращать право голоса можно только безопасной процедурой восстановления/изменения состава, сохраняющей подтверждённое состояние и исключающей повторное голосование. Недоступное состояние нельзя объявить восстановленным из произвольной отставшей реплики.
4. Потеря большинства не лечится автоматическим превращением свежих процессов в новый кворум. Новый пустой кластер/эпоха после невосстановимой потери — явная операция, объявляющая потерю старого состояния; недопустимо выдавать её за обычное продолжение старого кластера.
5. Взаимная аутентификация участников и ограниченный список состава. Внутрикластерное соединение не является публичной командой клиента. Шифрование и подписи — существующие разрешённые примитивы/проверенный транспорт, не самописная криптография.
6. Бюджет RAM ограничивает также неподтверждённые операции, очередь репликации, передачу снимка **в RAM**, повторы, дедупликацию и отставшую реплику. Медленный участник не создаёт неограниченный журнал; перегрузка получает ограниченный отказ.
7. Маршрут одного ID ведёт к одной группе-владельцу; ID отправителя и соответствующий ID получателя маршрутизируются согласованно. Независимые Store за случайным балансировщиком этому не соответствуют. Перенос группы/очереди требует протокола передачи полномочий.
8. Добавления клиента, batch и маршрутизации — отдельная версия/согласование возможностей, без тихого расширения wire v1. При потере ответа клиент не может считать операцию неисполненной: доставка остаётся «хотя бы раз».

## Матрица приёмки

Проверять исполняемую реализацию, а не имитацию трёх списков:

| Сценарий | Проверяемый результат |
| --- | --- |
| Один участник остановлен до/после SEND | Живое большинство продолжает работу; подтверждённые сообщения не исчезают |
| Разделение 2+1, в том числе старый лидер в меньшинстве | Успех записи только у большинства; нет двух независимых историй |
| Разделение 1+1+1 / потеря двух | Нет успешной записи без большинства |
| Ответ SEND потерян после фиксации | Повтор не ломает FIFO/ACK; дубликат допустим в заявленной модели |
| ACK/DEL во время смены лидера | Нет возврата удалённого сообщения/старой очереди |
| Перезапуск участника с пустой RAM | Нет немедленного голоса; ограниченное восстановление, затем безопасное возвращение |
| Два последовательных перезапуска и отставшая третья реплика | Не подтверждается восстановление отсутствующего подтверждённого префикса |
| Заполненная RAM / медленная реплика / разрыв передачи снимка | Конечная память, ограниченный отказ, нет ложного успеха |
| Полная потеря RAM кластера | Явная новая эпоха, очереди восстанавливает клиент, содержимое не обещается |

## Статус

На базовом SHA `84d3d4a056807043b96dcfd9bd7410fae42faa6b` и в первом пакете этой работы **нет** реализации consensus, peer RPC, multi-node routing, batch v2, шардированного Store или событийного I/O. `store.rs` и `server.rs` первого пакета исправляют bounded cleanup и admission памяти; они не дают HA. Перед фиксацией всего узла требуется закончить перечисленные компоненты, выполнить fault-injection и проверить развёртывание.
