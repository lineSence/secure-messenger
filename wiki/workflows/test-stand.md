# Стенд: один телефон, тестовый узел, ПК

Статус: **предложение** (2026-10-17, `5ce368c`). Не отменяет проверку на двух телефонах (ADR-59) и не заменяет релизное ИИ-ревью. Чек-лист приёмки — `wiki/workflows/acceptance-0.0.2.md`.

## 1. Задача и ограничения

Проверять сетевой путь и сценарии `0.0.2-alpha`, когда второго телефона нет: один телефон, тестовый узел на ПК и сам ПК.

Ограничения, из которых вытекает конструкция:

- клиент только Android, ядро `libsm_ffi.so` собирается только под `arm64-v8a` (ADR-46); Windows-клиента нет до `0.4.0` (ADR-22);
- в эмуляторе Android нет Bluetooth, BLE-путь им не проверить;
- приложение доверяет только системным CA, cleartext запрещён (ADR-72), ключ узла проверяется пином SPKI из подписанной записи;
- `sm-relay` слушает `127.0.0.1`; снаружи — TLS-прокси (nginx/Caddy, ADR-90);
- адрес узла — домен, не IP; порт и путь задаются в записи узла (`sm-node-tool sign --port --path`).

Следствие: ПК не может «просто быть вторым телефоном». Он либо хостит узел, либо запускает второй экземпляр клиента (эмулятор/headless), либо помогает через `adb` и сборку.

## 2. Что даёт ПК

| Роль | Даёт | Не даёт |
|---|---|---|
| Хост `sm-relay` + TLS | реальный сетевой путь, рестарт узла, `NO_QUEUE`, смена домена | второго собеседника |
| `adb` + debug-журнал | установка APK, `logcat`, снимки экрана, сценарии Doze | эмуляцию BLE |
| Work profile / второй экземпляр | второго собеседника на том же телефоне | BLE и независимую сеть |
| Эмулятор Android | полноценный второй клиент с UI | BLE, реальный вендор, реальный модем |
| Headless Rust peer | автоматизацию, нагрузку, точные замеры | UI и поведение Kotlin-слоя |

## 3. Уровни стенда

### L0 — один телефон и узел на ПК

Второго клиента нет. Проверяется связка «приложение ↔ узел»: приём записи `SMN1:` и пропуска `SMP1:`, состояния экрана «Связь», создание очереди (`NEW`), отказ `DENIED` при чужом/просроченном пропуске, переход на запасной домен, рестарт узла (`NO_QUEUE` → `NEW`), поведение в фоне, debug-журнал.

Не проверяется: доставка сообщения, ссылка-приглашение, BLE. Это быстрый smoke-тест узла и клиента, не приёмка.

### L1 — второй экземпляр на том же телефоне (work profile)

`Shelter` или `Island` (F-Droid) создают рабочий профиль; приложение клонируется туда и получает отдельные данные и ключи. Оба процесса живут одновременно, уведомления приходят из обоих.

Проверяется: ссылка-приглашение в обе стороны (вставка текста, не QR), обмен текстом через узел, статусы «на узле»/«доставлено», «Сведения о сообщении», фон и уведомления, удаление контакта, повторный рестарт узла.

Ограничения: один BLE-адаптер — GATT-сервер и клиент на одном телефоне не считаются проверкой BLE; свой QR не отсканировать; камера и «Рядом» не проверяются; рабочий профиль может засыпать агрессивнее личного.

Это самый дешёвый способ проверить `0.0.2` без второго телефона: не требует ни эмулятора, ни нового кода.

### L2 — эмулятор Android на ПК как второй телефон

AOSP API 31+ (`x86_64`). Нужно:

1. собрать ядро под `x86_64-linux-android` (сейчас `scripts/build-android-core.sh` жёстко задаёт `arm64-v8a` и `linux-x86_64` путь NDK; нужен параметр target и `jniLibs/x86_64` для debug);
2. `abiFilters` debug-варианта с `x86_64`;
3. Android SDK: emulator, system image API 31+, NDK r28; ~5 ГБ.

Проверяется: полный UI-поток, QR (камера эмулятора — виртуальная сцена), уведомления, Doze (`adb shell dumpsys deviceidle`), смена сети, установка debug поверх debug.

Не проверяется: BLE, реальный модем и вендорские ограничения фона. Релизная сборка остаётся `arm64-v8a`; `x86_64` — только debug для стенда, это отдельное решение (ADR).

### L3 — headless Rust peer (`sm-peer-tool`)

Отдельный бинарь в workspace на `sm-core` + `sm-signal` + `sm-relay`: идентичность, QR/ссылка, сессия Signal, кадры, сценарии (N сообщений с интервалом, обрыв, рестарт узла, задержка, потеря ACK), JSON-вывод. Может работать и как генератор нагрузки для узла.

Плюсы: воспроизводимо, автоматизируется в CI, не требует Android SDK, даёт точные метрики доставки и повторов. Минусы: новый инструмент, TLS-зависимость для HTTPS-режима (отдельный supply-chain/ADR), риск разойтись с Kotlin `RelayHub` — тестировать надо и клиент, и протокол.

Проверяется: доставка/ACK/повторы, TTL, рестарт и `NO_QUEUE`, лимиты, задержка, поведение при потере ответа. Не проверяется: UI, фон Android, разрешения.

### L4 — BLE

Только второй физический телефон — эталон. Альтернатива для ПК — BLE-периферия (GATT-сервер через WinRT) и реализация `PairLink`/`PairFrame` на ПК; это отдельный проект, в первые этапы не входит.

## 4. Узел на ПК: три варианта TLS

Приложение принимает только цепочку до системного CA и пин SPKI из записи. Самоподписанный сертификат без доверия к CA не подойдёт.

| Вариант | Как | Цена |
|---|---|---|
| A. Публичный домен + DNS-01 | Caddy/nginx, сертификат Let's Encrypt по DNS-01, A-запись на внешний IP или LAN-IP | нужен домен и API DNS; работает и с мобильной сети |
| B. LAN: `sslip.io` + mkcert | имя `192-168-1-5.sslip.io` → LAN-IP, сертификат mkcert, CA установлен на телефон, `debug-overrides` в `network_security_config` | правка конфига (только debug) и ADR; телефон должен быть в той же LAN |
| C. VPS | существующий тестовый узел | ПК не хост; LAN-сценарии не проверяются |

Вариант B по шагам:

1. `mkcert -install`, `mkcert 192-168-1-5.sslip.io` (имя подставить своё).
2. Caddy/nginx слушает `8443`, проксирует секретный путь на `127.0.0.1:7400` (режим `SM_RELAY_MODE=http`), `reuse_private_keys`.
3. Разрешить входящий `8443` в брандмауэре Windows; телефон — в той же Wi-Fi.
4. Пин: `openssl s_client -connect 127.0.0.1:8443 -servername ИМЯ | openssl x509 -pubkey -noout | openssl pkey -pubin -outform der | openssl dgst -sha256 -r`.
5. `sm-node-tool sign root.key --domain ИМЯ --pin ПИН --port 8443 --path /СЕКРЕТНЫЙ_ПУТЬ --days 30`, затем `sm-node-tool pass root.key --per-hour 20 --days 30`.
6. На телефоне: установить CA mkcert как пользовательский сертификат, открыть HTTPS-адрес в браузере (проверка цепочки), принять `SMN1:` и `SMP1:` в приложении.

Для варианта B нужен debug-APK с `<debug-overrides><trust-anchors><certificates src="user"/></trust-anchors></debug-overrides>` в `network_security_config.xml`: это стандартный механизм Android, действует только на debuggable-сборку и не меняет release. Правка требует ADR: она расширяет доверие в debug, хотя и не в релизе.

Рестарт узла на ПК стирает очереди — это ожидаемое поведение RAM-only, его и надо проверять.

## 6. Что стенд не доказывает

- реальный BLE и его поведение в фоне;
- два разных устройства и две реальные сети (L1 — один адаптер, L2 — эмулятор);
- вендорские ограничения фона и Doze (Xiaomi, Samsung и т.п.);
- что release-APK ведёт себя как debug (debug-overrides, `x86_64`, debug-журнал);
- приёмку `0.0.2` — её закрывает только прогон по `acceptance-0.0.2.md` на двух телефонах.

## 7. Ближайшие шаги

1. Прогнать L0 и L1 на текущем debug-APK и тестовом узле — это уже даёт большую часть сетевых проверок.
2. Решить по L2: ADR на `x86_64` debug-сборку ядра и `abiFilters`.
3. Решить по L3: ADR на `sm-peer-tool` (зависимости, supply-chain, границы «не заменяет приложение»).
4. BLE — только вторым телефоном; BLE-периферию на ПК не начинать до L2/L3.
