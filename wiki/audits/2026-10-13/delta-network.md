# Summary

READ-ONLY delta-аудит `c0c9059b041a787a2d2ac4aa1823b99ed1aaee68` → `9595f2e127b96dd37fa81fd32d41f18bd48e9896` (PR89, merge — по контексту задания). **2 новых Medium availability-находки и 1 Low recovery-дефект**; ни один не объявляется взломом Signal/утечкой текста. Исправление fallback снимает прямой запрет relay при BLE-метке, но два транспорта всё ещё конкурируют за один consumed retry. Новый Pair mailbox переносит блокирующий HTTPS на pairing worker и связывает его с общим BLE budget/relay admission lock.

| ID | Severity | Результат / доказательство |
|---|---|---|
| DELTA-NET-1 | Medium | Неудачный relay захватывает попытку здорового подключённого BLE; native Outbox probe подтверждает подавление до часа при указанном расписании. Android race не воспроизведён. |
| DELTA-NET-2 | Medium | Медленный `NEW` под общим mailboxLock блокирует pairing worker и подготовку очередей приёма; queued Pair frames удерживают все 32 глобальных BLE permits даже после UI timeout. Настоящие PairMailboxExchange/InboundBudget + явная scheduler/port модель. |
| DELTA-NET-3 | Low | Relay sender backoff стал непрерываемым `Thread.sleep`: смена сети/wake не возвращает отправку раньше окончания паузы, до 5 минут. По коду. |

**Старые:** AUD-01 — открыт; AUD-02 — открыт; AUD-03 — открыт. HYP-PAIR-BUDGET — частично ограничен только новый completed-mailbox worker путь, raw callbacks всё ещё вне budget, ANR/OOM не доказаны. HYP-HTTPS-DEADLINE — открыт; новый общий lock/worker усиливает последствия, но endpoint exploit в Android не проверен.

**Проверки:** 37 JVM tests passed (33 mailbox/freshness/frame-cache/ack + 4 sender); native probe 8 неудачных попыток/подавление BLE; JVM scheduling/budget probe passed. Checkout не изменён. Это ограниченный delta-аудит, не release verdict, не полный Android/Gradle/BLE/TLS аудит.

## Детали

### DELTA-NET-1 — Общий retry потребляется relay до результата, поэтому рабочий BLE не получает кадр

**Severity: Medium (доступность), уверенность: высокая в механизме, условная в длительном расписании.**

**Места:** [`android/app/src/main/java/dev/sm/messenger/relay/RelayHub.kt:343–364`](https://github.com/lineSence/secure-messenger/blob/9595f2e127b96dd37fa81fd32d41f18bd48e9896/android/app/src/main/java/dev/sm/messenger/relay/RelayHub.kt#L343-L364) — изменённый путь теперь всегда вызывает sendTo, включая рядом/подключённый BLE; [`android/app/src/main/java/dev/sm/messenger/chat/ChatHub.kt:265–312`](https://github.com/lineSence/secure-messenger/blob/9595f2e127b96dd37fa81fd32d41f18bd48e9896/android/app/src/main/java/dev/sm/messenger/chat/ChatHub.kt#L265-L312) — gather отмечает `attempted` для всего собранного batch ещё до SEND; [`android/app/src/main/java/dev/sm/messenger/relay/RelayFrameSender.kt:10–14`](https://github.com/lineSence/secure-messenger/blob/9595f2e127b96dd37fa81fd32d41f18bd48e9896/android/app/src/main/java/dev/sm/messenger/relay/RelayFrameSender.kt#L10-L14) — ошибка send прерывает batch. BLE использует тот же gather: [`android/app/src/main/java/dev/sm/messenger/ble/BleHub.kt:244–247`](https://github.com/lineSence/secure-messenger/blob/9595f2e127b96dd37fa81fd32d41f18bd48e9896/android/app/src/main/java/dev/sm/messenger/ble/BleHub.kt#L244-L247). Настройки/механизм backoff: [`crates/sm-core/src/delivery.rs:54–61`](https://github.com/lineSence/secure-messenger/blob/9595f2e127b96dd37fa81fd32d41f18bd48e9896/crates/sm-core/src/delivery.rs#L54-L61), [`crates/sm-core/src/delivery.rs:212–244`](https://github.com/lineSence/secure-messenger/blob/9595f2e127b96dd37fa81fd32d41f18bd48e9896/crates/sm-core/src/delivery.rs#L212-L244).

**Предпосылки / impact:** интернет определяется доступным, peer route записан, SEND этому relay не проходит (сбой/блокировка либо контролируемый pinned endpoint), BLE уже подключён и исправен. Когда sweep relay попадает на due перед BLE collect, он потребляет общую попытку. Даже если первый SEND сразу бросает исключение, все собранные сообщения уже перенесены на будущий срок; здоровый BLE получает пустой список. Повторение такого порядка растит задержку до часа. Это не обязательный исход каждого запуска: если BLE collect выигрывает, он доставляет; reconnect принудительно делает сообщения due. Получение настоящего Signal ACK тоже завершает сообщение. Не заявляется возможность произвольного соседа управлять HTTPS через MITM.

**Почему delta:** ранее near gate не давал relay собирать кадры для видимого соседа. Его снятие правильно разрешает fallback на relay, но открывает обратное вмешательство неисправного relay в здоровый BLE. Общая outbox/cache остаётся правильной для единого ciphertext, но единый consumed retry не обеспечивает независимость транспортов.

**Proof:** `delta-network-tmp/fallback.rs` связан с **текущим** sm-core, собранным напрямую rustc. После `attempted` на времени due модель считает relay send неудачным и проверяет BLE каждые 30 секунд с фазой +1 ms. Паузы: 60/120/240/480/960/1920/3600/3600 секунд; все BLE ticks до следующего due пусты. Control: при старом near gate попытка не потребляется и BLE due остаётся. Лог `fallback.log`. Это native API + заданный scheduler, не выполнение полного ChatHub/Android и не доказательство устойчивого выигрыша relay на телефоне. Первый compile probe потребовал исправить тип Key в **тесте**, production не тронут.

**Correction:** одна durable очередь и один cached ciphertext, но независимый bounded transport retry (или один dispatch batch, доступный обоим каналам). Не расходовать попытку другого маршрута при сборе; result одного транспорта не должен делать кадр невидимым исправному второму. Regression: подключённый BLE, relay SEND fail, relay gather раньше BLE; кадр всё равно передан BLE в его следующем окне, включая остальные кадры batch после первого исключения.

### DELTA-NET-2 — Медленный prepare переживает timeout и связывает pairing с глобальным BLE budget

**Severity: Medium (доступность), уверенность: высокая в блокировках/budget, exploit runtime ограничен.**

**Места:** [`android/app/src/main/java/dev/sm/messenger/relay/RelayHub.kt:279–319`](https://github.com/lineSence/secure-messenger/blob/9595f2e127b96dd37fa81fd32d41f18bd48e9896/android/app/src/main/java/dev/sm/messenger/relay/RelayHub.kt#L279-L319) — новый общий mailboxLock, `relay.newQueue` внутри lock, затем синхронный ChatHub вызов; [`android/app/src/main/java/dev/sm/messenger/contacts/Pairing.kt:349–426`](https://github.com/lineSence/secure-messenger/blob/9595f2e127b96dd37fa81fd32d41f18bd48e9896/android/app/src/main/java/dev/sm/messenger/contacts/Pairing.kt#L349-L426) — prepare на single worker, timeout лишь закрывает mailbox/UI, обработчики кадров стоят на том же worker; [`android/app/src/main/java/dev/sm/messenger/contacts/PairMailboxExchange.kt:26–38`](https://github.com/lineSence/secure-messenger/blob/9595f2e127b96dd37fa81fd32d41f18bd48e9896/android/app/src/main/java/dev/sm/messenger/contacts/PairMailboxExchange.kt#L26-L38) — timeout проверен перед блокирующим prepare, не ограничивает сам вызов; shared budget: [`android/app/src/main/java/dev/sm/messenger/ble/InboundBudget.kt:13–37`](https://github.com/lineSence/secure-messenger/blob/9595f2e127b96dd37fa81fd32d41f18bd48e9896/android/app/src/main/java/dev/sm/messenger/ble/InboundBudget.kt#L13-L37). Зависимость общего BLE приёма: [`android/app/src/main/java/dev/sm/messenger/ble/BleLink.kt:317–329`](https://github.com/lineSence/secure-messenger/blob/9595f2e127b96dd37fa81fd32d41f18bd48e9896/android/app/src/main/java/dev/sm/messenger/ble/BleLink.kt#L317-L329).

**Предпосылки / impact:** pairing дошёл до сохранённой сессии, локальный account имеет node/pass и требуется NEW. Контролируемый/компрометированный **pinned** собственный endpoint может задерживать ответ под readTimeout либо случается долгий сетевой сбой. Пока prepare висит, relay receive ждёт mailboxLock ещё до FETCH/WAIT, а новые задачи pairing стоят за prepare. Если активный сопрягаемый peer присылает 32 small zero-mailbox frames, они занимают InboundBudget и ждут этот worker; AEAD внешних частей должен уже проходить, Signal ciphertext может быть мусором. Этот budget глобальный: обычный BleLink отвергает кадры других контактов. Timeout на 60 s, disconnect или close не освобождают permits: release находится в finally ещё не стартовавших задач; `worker.shutdown()` не прерывает running task. UI может уже показывать Done, хотя worker и permits ещё заняты.

Задержка одного NEW не сама по себе новый HTTPS defect: **новое — общий mailboxLock и размещение prepare перед budgeted кадрами на pairing executor**, что переносит зависимость relay endpoint на локальный BLE/дальнейшее сопряжение. Без кадров исчерпания budget нет, но shared lock/worker остаются заблокированы. Память этих completed frames ограничена 32 frames/1 MiB; OOM этим механизмом не заявляется. Произвольный неаутентифицированный BLE сосед/обычный MITM не объявляются достаточными для полного сценария.

**Proof:** `delta-network-tmp/Probe.kt` использует настоящие PairMailboxExchange и InboundBudget, single executor и явно **заглушенный blocking port.prepare** с latch; общий lock моделирует точный порядок RelayHub. Проверены: 32 permits удержаны, 33-й acquire отвергнут, второй executor не получает lock, UI completion не завершает task, permits освобождаются только после возврата prepare. `budget.log` — PASS. Это proof control-flow, **не настоящий HttpsRelay, Pairing, Handler, radio или pinned endpoint flood**. Нет измерений ANR/OOM. Slow-response Android test остаётся нужен.

**Correction:** не держать mailboxLock на HTTPS и `.get()`; резервировать bounded in-flight создание короткой критической секцией, завершение commit — только после проверки актуальности. Для prepare нужен общий monotonic deadline и реальное cancel/disconnect, отдельный ограниченный IO executor; session timeout должен отменять работу и освобождать queued frame permits (с защитой от double-release). Разделить per-session Pair budget и обычный BLE admission, чтобы вспомогательное сопряжение не могло занять всё. Regression: stuck NEW + 32 входа + timeout/disconnect; приём старого контакта и новый pairing остаются работоспособны, permit counters возвращаются, late prepare не меняет отменённую session.

### DELTA-NET-3 — wake перестал прерывать sender backoff

**Severity: Low, availability/recovery-дефект, не самостоятельный remote exploit.**

**Места:** [`android/app/src/main/java/dev/sm/messenger/relay/RelayHub.kt:133–194`](https://github.com/lineSence/secure-messenger/blob/9595f2e127b96dd37fa81fd32d41f18bd48e9896/android/app/src/main/java/dev/sm/messenger/relay/RelayHub.kt#L133-L194) — sender теперь спит Thread.sleep, bell слушает только receiver; [`android/app/src/main/java/dev/sm/messenger/relay/RelayHub.kt:343–348`](https://github.com/lineSence/secure-messenger/blob/9595f2e127b96dd37fa81fd32d41f18bd48e9896/android/app/src/main/java/dev/sm/messenger/relay/RelayHub.kt#L343-L348) — outgoing poll помогает лишь когда поток уже вернулся из сна; [`android/app/src/main/java/dev/sm/messenger/relay/RelayPolicy.kt:101–105`](https://github.com/lineSence/secure-messenger/blob/9595f2e127b96dd37fa81fd32d41f18bd48e9896/android/app/src/main/java/dev/sm/messenger/relay/RelayPolicy.kt#L101-L105), [`android/app/src/main/java/dev/sm/messenger/relay/RelayPolicy.kt:123–124`](https://github.com/lineSence/secure-messenger/blob/9595f2e127b96dd37fa81fd32d41f18bd48e9896/android/app/src/main/java/dev/sm/messenger/relay/RelayPolicy.kt#L123-L124) — retry cap до 300000 ms.

**Предпосылки / impact:** sender уже в backoff после ошибок, сеть/узел восстановились или пользователь отправил новое сообщение/принял новую запись узла. switchChannel сбрасывает schedule и предлагает bell, wake тоже предлагает bell, но sleeping sender ничего из этого не видит. Фактическая уже рассчитанная пауза сохраняется, до 5 минут; outgoing может накапливаться, но бесконечный рост или удалённое создание произвольного количества сообщений здесь не доказаны. Старый shared bell мог достаться другому потоку, поэтому это не утверждение, что раньше каждый wake гарантированно будил sender; delta сделала его заведомо непрерываемым.

**Proof boundary:** статический control-flow; отдельный Android timing тест не выполнен. Новые RelayFrameSender tests этого lifecycle не покрывают.

**Correction:** отдельные bounded/coalesced wake channels для sender и receiver либо interruptible wait по sender condition/deadline. Будить sender на network switch и новом outgoing, не удаляя anti-flood/backoff policy на persistently failing endpoint. Regression: sender в максимальном backoff, network switch/новое outgoing → обработка сразу согласно обновлённой policy, независимо от receiver bell.

## Положительные изменения и ограничения

- PeerFreshness отвергает отрицательные/future timestamps и истечение независимо от prune; periodic prune добавлен в BleHub. 2 соответствующих JVM tests passed. Это не аутентификация beacon/admission.
- RelayFrameSender помечает on-node только после нормального возврата send; 4 tests passed, включая failed send. Нативный cache ciphertext не пересоздаётся между транспортами; FrameCache tests passed.
- PairMailboxExchange различает GATT и Signal ACK, лимитирует batch 8 и имеет 60-s state-machine timeout. 9 mailbox tests passed; deadline проверки step не означает deadline блокирующего prepare.
- Прочитаны AGENTS.md, старый report.md/network.md и релевантные кодовые правила. Основная область: diff BleHub/PeerFreshness, RelayHub/RelayFrameSender, PairLink и новый Pairing/PairMailboxExchange raw-mailbox путь; ChatHub/FrameCache только как transport dependencies. UI, Signal handshake internals, storage correctness, полный Rust workspace и supply-chain не переаудированы.
- Использованы существующие Rust/compiler/JVM jars; tools не устанавливались, subagents не запускались, GitHub/Notion/checkout не правились. Все generated probes/builds/logs в `/data/security-fix/delta-network-tmp/`. Никакие секреты/production endpoints не использовались. Standalone rustc build не является cargo test/clippy/full CI.
- JVM существующие tests: `junit.log` 33 passed, `relay-tests.log` 4 passed. `budget.log` — отдельная модель; `fallback.log` — native API со смоделированным scheduler. Эти числа не обозначают количество независимых exploits.
