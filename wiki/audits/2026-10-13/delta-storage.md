## AUD11: что действительно исправлено

[android/app/src/main/java/dev/sm/messenger/chat/ChatHub.kt:345-364](https://github.com/lineSence/secure-messenger/blob/9595f2e127b96dd37fa81fd32d41f18bd48e9896/android/app/src/main/java/dev/sm/messenger/chat/ChatHub.kt#L345-L364)

Новый queueMailbox сначала фиксирует `chat_send` в SQL, затем push в RAM. Успешный snapshot разрешает убрать journal; неуспешный оставляет его. Ошибка push удаляет только что созданный journal и возвращает отказ через guard: это **не** исходный false-success AUD11. own/told фиксируются лишь после успешной постановки в очередь. [android/app/src/main/java/dev/sm/messenger/relay/RelayHub.kt:279-300](https://github.com/lineSence/secure-messenger/blob/9595f2e127b96dd37fa81fd32d41f18bd48e9896/android/app/src/main/java/dev/sm/messenger/relay/RelayHub.kt#L279-L300)

При обычном завершении процесса после failed snapshot journal восстанавливает Mailbox, если outbox может принять его. Стенд подтвердил этот контрольный сценарий. Crash после успешного snapshot, но до удаления journal также допускает идемпотентный replay: existing `(mailbox,id)` пропускается. Durable CT/tombstone предотвращает повторное шифрование/отправку уже подтверждённого сообщения. [android/app/src/main/java/dev/sm/messenger/chat/ChatHub.kt:219-235](https://github.com/lineSence/secure-messenger/blob/9595f2e127b96dd37fa81fd32d41f18bd48e9896/android/app/src/main/java/dev/sm/messenger/chat/ChatHub.kt#L219-L235) [android/app/src/main/java/dev/sm/messenger/chat/FrameCache.kt:45-60](https://github.com/lineSence/secure-messenger/blob/9595f2e127b96dd37fa81fd32d41f18bd48e9896/android/app/src/main/java/dev/sm/messenger/chat/FrameCache.kt#L45-L60)

## DELTA-STO-1 — failed replay удаляется вместе с успешными записями

**Severity: Medium.** Новое обнаружение, связанное с частичным исправлением AUD11; общий дефект recoverQueue существовал для текста до delta.

**Точное место:** [android/app/src/main/java/dev/sm/messenger/chat/ChatHub.kt:219-235](https://github.com/lineSence/secure-messenger/blob/9595f2e127b96dd37fa81fd32d41f18bd48e9896/android/app/src/main/java/dev/sm/messenger/chat/ChatHub.kt#L219-L235); вход нового пути: [android/app/src/main/java/dev/sm/messenger/chat/ChatHub.kt:345-364](https://github.com/lineSence/secure-messenger/blob/9595f2e127b96dd37fa81fd32d41f18bd48e9896/android/app/src/main/java/dev/sm/messenger/chat/ChatHub.kt#L345-L364); ограничения push: [crates/sm-core/src/delivery.rs:176-187](https://github.com/lineSence/secure-messenger/blob/9595f2e127b96dd37fa81fd32d41f18bd48e9896/crates/sm-core/src/delivery.rs#L176-L187).

**Предпосылки:** snapshot содержит заполненную очередь (1000 сообщений либо лимит байтов); live outbox уже освободила место после ACK, но этот confirm ещё не попал на диск. queueMailbox принимает новое сообщение и сохраняет journal; запись snapshot не удаётся. own/told пишутся успешно. Процесс завершается до удачного deferred save. Позже восстановление snapshot/save снова работоспособно. Не требуется удалённый атакующий; контакт с большим backlog может способствовать quota, но удалённый exploit не доказан.

**Последовательность:**
1. На диске старый full snapshot; в RAM после confirm есть место.
2. Mailbox push успешен, save=false, journal остаётся, вызывающий RelayHub фиксирует own/told.
3. После restart восстанавливается старый full snapshot; Mailbox в нём нет.
4. recoverQueue делает push → Full; catch только пытается `messages.setState(Failed)`. У служебного Mailbox строки истории вообще нет.
5. Сохранение заполненной очереди успешно; строка 235 удаляет **все** entries, в том числе не попавший в outbox Mailbox.
6. Теперь нет ни journal, ни Mailbox в snapshot. Существующие own текущего периода и told текущего node препятствуют повторному объявлению. Контакт остаётся без актуального маршрута; обычные retry outbox его не восстановят.

**Proof boundary:** `Probe.kt` содержит точно извлечённые текущие тела queueMailbox и recoverQueue, текущий SendEntry. Persistence и FFI заменены картами, quota уменьшена до 2 для краткого контрпримера. Assertions проверяют: ID принят; journal есть при failed save; после моделируемого restart Full; после replay journal пуст, ID в durable snapshot отсутствует. Rust-код отдельно подтверждает такой Full до вставки. Это JVM control-flow proof, не kill-test реальной SQLite/AtomicFile. Параллельная запись старого snapshot не нужна.

**Fix:** удалять journal только для конкретных entries, чьё включение в успешно записанный snapshot проверено, либо для durable terminal/cancelled outcome. Full должен сохранять запись и повторять admission после освобождения места, а не только при следующем attach. Перед admission очистить из восстановленной outbox записи с durable ACK/cancellation tombstones. Для Mailbox terminal failure нельзя молча скрывать за отсутствующей строкой истории: связать pending announcement с ID/состоянием либо сбрасывать own/told только по определённой durable процедуре. Regression: full old snapshot → unsaved confirm → accepted Mailbox + failed save → restart → journal остаётся → место освобождается → тот же ID восстанавливается и доставляется.

## DELTA-STO-2 — mailbox preparation не участвует в удалении контакта

**Severity: Low.** Новое обнаружение существовавшей гонки ensureQueues/dropContact; delta добавляет preparePairMailbox с тем же отсутствием cancellation/generation check. Не считать новой регрессией самого ensureQueues.

**Точные места:** [android/app/src/main/java/dev/sm/messenger/relay/RelayHub.kt:279-300](https://github.com/lineSence/secure-messenger/blob/9595f2e127b96dd37fa81fd32d41f18bd48e9896/android/app/src/main/java/dev/sm/messenger/relay/RelayHub.kt#L279-L300), [android/app/src/main/java/dev/sm/messenger/relay/RelayHub.kt:304-319](https://github.com/lineSence/secure-messenger/blob/9595f2e127b96dd37fa81fd32d41f18bd48e9896/android/app/src/main/java/dev/sm/messenger/relay/RelayHub.kt#L304-L319), [android/app/src/main/java/dev/sm/messenger/chat/ChatHub.kt:506-532](https://github.com/lineSence/secure-messenger/blob/9595f2e127b96dd37fa81fd32d41f18bd48e9896/android/app/src/main/java/dev/sm/messenger/chat/ChatHub.kt#L506-L532), [android/app/src/main/java/dev/sm/messenger/contacts/ContactBook.kt:111-119](https://github.com/lineSence/secure-messenger/blob/9595f2e127b96dd37fa81fd32d41f18bd48e9896/android/app/src/main/java/dev/sm/messenger/contacts/ContactBook.kt#L111-L119), [android/app/src/main/java/dev/sm/messenger/relay/OwnQueues.kt:50-57](https://github.com/lineSence/secure-messenger/blob/9595f2e127b96dd37fa81fd32d41f18bd48e9896/android/app/src/main/java/dev/sm/messenger/relay/OwnQueues.kt#L50-L57).

**Предпосылки:** пользователь удаляет контакт, пока relay/поток сопряжения готовит его очередь. NEW уже начат или worker ещё не поставил Mailbox на sm-chat. Удаление завершается успешно; сеть затем отвечает успешно. Не требуется SQL failure или crash.

**Schedule:** ensureQueues получает список контактов и входит в NEW; NEW задерживается. sm-chat удаляет outbox и SQL contact/Signal/journal/own/peer/told. NEW возвращается. ensureQueues продолжает с сохранённым объектом контакта, sendMailbox не проверяет существование/поколение контакта, и заново записывает pending announcement, own и told. mailboxLock сериализует ensureQueues с preparePairMailbox, но dropContact его не берёт. preparePairMailbox принимает голый address и тоже не проверяет актуальность контакта после сети.

**Последствия:** успешное удаление не гарантирует удаления всех связанных очередей/служебных данных. Появляются orphan outbox/own/told; в отсутствии сессии gather не может зашифровать pending Mailbox, поэтому запись может занимать общую quota до следующего удаления/ручного восстановления. Завершившийся callback удаления не знает о поздней NEW-очереди и не закрывает её. **Не утверждается**, что удалённый контакт возвращается в ContactBook, что очередь такого контакта автоматически опрашивается после удаления, или что он получает новый plaintext. Low: локальное действие и узкая конкурентная schedule, эффект прежде всего lifecycle/resource consistency.

**Proof boundary:** Race.kt исполняет точный текущий ensureQueues. CountDownLatch останавливает NEW; модель удаления чистит contact/pending/own/told; затем NEW разблокирован. Assertions: contact отсутствует, pending/own/told появились. Book/SQL/NEW/queueMailbox — заглушки, не Android instrumentation; достижимость реального schedule следует из отсутствия удерживаемого SQL/gate во время NEW и сериализации отдельного sm-chat executor.

**Fix:** сеть делать без DB/Signal/lifecycle locks. На sm-chat после ответа атомарно проверить contact rowId/generation и commit durable Mailbox intent + own/told; удалить/отменить intent вместе с контактом. Удаление должно увеличивать generation/оставлять durable cancellation, чтобы stale сетевой результат не мог resurrect state. Не добавлять mailboxLock вокруг ожидания io.get в dropContact: это способно создать новый lock cycle. Если NEW уже завершён для отменённого generation, закрыть/долговечно записать на уборку его queue ID. Barrier regression с настоящей SQL: delete завершается, NEW возвращается, никакие pending/own/told не возникают.

## DELTA-STO-3 — tombstone ошибки выдаётся за Signal delivery

**Severity: Low.** Новая семантика `mailboxDelivered`/PairMailboxExchange; существующий общий failure tombstone был до delta.

**Точные места:** [android/app/src/main/java/dev/sm/messenger/chat/ChatHub.kt:287-299](https://github.com/lineSence/secure-messenger/blob/9595f2e127b96dd37fa81fd32d41f18bd48e9896/android/app/src/main/java/dev/sm/messenger/chat/ChatHub.kt#L287-L299), [android/app/src/main/java/dev/sm/messenger/chat/ChatHub.kt:371-372](https://github.com/lineSence/secure-messenger/blob/9595f2e127b96dd37fa81fd32d41f18bd48e9896/android/app/src/main/java/dev/sm/messenger/chat/ChatHub.kt#L371-L372); [android/app/src/main/java/dev/sm/messenger/chat/FrameCache.kt:55-60](https://github.com/lineSence/secure-messenger/blob/9595f2e127b96dd37fa81fd32d41f18bd48e9896/android/app/src/main/java/dev/sm/messenger/chat/FrameCache.kt#L55-L60), [android/app/src/main/java/dev/sm/messenger/contacts/PairMailboxExchange.kt:25-40](https://github.com/lineSence/secure-messenger/blob/9595f2e127b96dd37fa81fd32d41f18bd48e9896/android/app/src/main/java/dev/sm/messenger/contacts/PairMailboxExchange.kt#L25-L40), [android/app/src/main/java/dev/sm/messenger/contacts/Pairing.kt:384-401](https://github.com/lineSence/secure-messenger/blob/9595f2e127b96dd37fa81fd32d41f18bd48e9896/android/app/src/main/java/dev/sm/messenger/contacts/Pairing.kt#L384-L401).

**Предпосылки:** `chat_ct` для ожидаемого Mailbox читается как CorruptFrame (повреждение/подмена приватной строки или локальный криптографический отказ, отображённый этой веткой), а запись новой tombstone возможна; peer mailbox уже есть. Не обычный сетевой ввод.

**Цепочка:** gather catch(CorruptFrame) подтверждает/убирает сообщение из RAM outbox и вызывает `frames.delivered`, хотя Signal ACK не приходил. isDelivered определяет ACK как любой пустой CT. После gather PairMailboxExchange видит hasPeer=true и delivered=true, выдаёт Complete(ready=true). Код, называющий это «подтверждением внутри Signal», больше не соблюдает этот контракт.

**Последствия/граница:** false-positive готовность и DiagnosticResult.Ok. Само прекращение отправки при corrupt CT уже существовало и не прибавляется как независимая новая потеря. В текущем Pairing finishMailbox вызывается для ready=true **и** false: дополнительного обхода trust/контактного подтверждения/изменения UI только вследствие этого флага не показано. Поэтому **Low**, не Medium и не forgery Signal ACK. Нельзя использовать этот API как доказательство peer acceptance без разделения состояний.

**Proof boundary:** текущие FrameCache и PairMailboxExchange исполняются на JVM, запись KV и CorruptFrame смоделированы; failure-переход gather повторён отдельно. Нет вызова Signal receive/ACK. Стенд проверяет Complete(ready=true) после этой tombstone; это не end-to-end повреждение реального Android файла.

**Fix:** различать authenticated Delivered, Failed/Cancelled и cached ciphertext в durable состоянии; outFrame может подавлять повтор всех terminal states, но isDelivered должен принимать только authenticated Delivered. При CorruptFrame писать Failed, не ACK tombstone. Добавить тест: CorruptFrame для Mailbox + existing peer → ready не становится true, отдельный diagnostic failure.

- **AUD12:** [android/app/src/main/java/dev/sm/messenger/chat/ChatHub.kt:506-532](https://github.com/lineSence/secure-messenger/blob/9595f2e127b96dd37fa81fd32d41f18bd48e9896/android/app/src/main/java/dev/sm/messenger/chat/ChatHub.kt#L506-L532) сначала confirm/save AtomicFile, затем SQL delete. При позднем SQL failure контакт/история остаются, сообщения из durable outbox уже исчезли. Новая journal запись Mailbox не восстанавливает ранее snapshot-committed сообщения: их journal уже удалён. Fix — durable cancellation/delete intent, согласованное восстановление по одной source of truth; SQL rollback не считать rollback AtomicFile.

- JVM fault/control probes: PROBE-1 lost journal, контрольный успешный replay; PROBE-2 failure tombstone false-ready; PROBE-3 delete/NEW race.
