## DELTA-PLAT-1 — failed tombstone ≠ подтверждение доставки

**Severity: Low. Доказательство: достижимая цепочка по настоящему коду + изолированный JVM probe; не Android end-to-end.**

### Exact lines / proof chain

Новый `FrameCache.isDelivered()` объявляет любой пустой CT-row подтверждённым внутри Signal: [`android/app/src/main/java/dev/sm/messenger/chat/FrameCache.kt:55–62`](https://github.com/lineSence/secure-messenger/blob/9595f2e127b96dd37fa81fd32d41f18bd48e9896/android/app/src/main/java/dev/sm/messenger/chat/FrameCache.kt#L55-L62).

Не следует расширять finding до «ложной доставки текста».

### Prerequisites / reproduction

Нужно: сохранённый контакт; его допустимая почта уже известна (независимо от ACK нашего сообщения); собственное служебное mailbox-сообщение ещё в outbox, а его сохранённый CT-кадр при чтении выдаёт CorruptFrame. Такое возможно при локальной порче/подмене зашифрованной строки; обычному BLE-соседу возможность изменять приватную БД не показана. Нет требования ломать Signal или Keystore.

На следующем gather: исключение → terminal пустой CT → список кадров может быть пуст → `isDelivered=true` → `Complete(true)` → debug `ChatMailbox/Ok`, хотя peer наше mailbox-сообщение не подтверждал. Старый маркер существовал до delta; **новое ошибочное значение «Signal ACK» и использование его в exchange введены этой delta**, поэтому finding не дублирует AUD-17.

Probe: `/data/security-fix/platform-tests/FalseReadyProbe.kt`; использует настоящие `FrameCache` и `PairMailboxExchange`, in-memory FrameKv и явно моделирует только catch-ветку gather (без Android/outbox/Signal). Проверяет ready=true без вызова receive/Signal ACK. **Probe: PASS, 1 test** (`probe.log`): `failure tombstone -> ready=true, without any Signal ACK`. Модель не доказывает runtime-поведение Android/Keystore; неоднозначность маркера и результат exchange подтверждены настоящими классами.

### Fix / regression

Разделить terminal состояния `DeliveredBySignal` и `FailedCorrupt` (отдельный тип/таблица/версионированный маркер). `outFrame` должен подавлять повторное шифрование в обоих состояниях, но `mailboxDelivered` обязан возвращать true только для настоящего ACK. Не удалять failed marker с повторным шифрованием! Учесть миграцию старых неоднозначных пустых rows: не объявлять их автоматически ACK.

Добавить failing regression через настоящий gather/port: corrupt CT собственного mailbox при существующем peer не даёт `ready=true` и `ChatMailbox/Ok`; настоящий Signal Delivered даёт true; отсутствие строки и failed marker — false. Instrumentation с повреждённой строкой SecureDb отдельно.
