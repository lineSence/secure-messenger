# UX/UI-аудит текущего main — 2026-10-14

## Итог и границы

Проверен **`0ccfbaa80eba483ea6c2cf6b83a6b80026235bae`**, `main` на начало проверки и на контрольный fetch перед подготовкой публикации: [commit](https://github.com/lineSence/secure-messenger/commit/0ccfbaa80eba483ea6c2cf6b83a6b80026235bae). Это уже merge PR #91: новый первый запуск v16 и исправление, не допускающее сохранения секретов приглашения в Bundle. Фиксы #89 также включены.

**После объединения — 30 замечаний: 21 × P2, 9 × P3. P1 в проверенных сценариях не доказан.** В число входит один пробел защиты от UI-регрессий (UI-07); остальные относятся к пользовательскому поведению/отображению. Это не 30 воспроизведённых на телефоне сбоев и не 30 новых security-уязвимостей. Есть ранее известные и унаследованные проблемы, отмеченные ниже.

- **P1:** блокирующий/критический дефект; отсутствие доказанных P1 не означает отсутствия таких ошибок.
- **P2:** существенный срыв сценария, потеря ввода, неверное состояние или затруднённое восстановление.
- **P3:** локальная путаница, недостаток семантики/обратной связи либо тестовой защиты.

Основное доказательство — **статическое прослеживание конкретного SHA**. Дополнительно выполнены SQL-модель, расчёт контраста и локальный рендер HTML-макета. **APK, Android/JVM/Compose-тесты, TalkBack и реальные телефоны не запускались; пиксельная приёмка Compose не выполнена.** Штатный Android-рендер не стартовал из-за отсутствующей конфигурации toolchain. Полные команды, результаты и ограничения — [verification.md](verification.md).

Аудит не устанавливает исходную причину ранее наблюдавшихся владельцем сбоев ссылок и пустого «Рядом», не является криптографическим аудитом или разрешением выпуска. Код, протоколы, макеты, проверки CI и release verdicts не менялись.

## Как организована работа

Четыре субагента текущей модели работали параллельно по разным областям и одному SHA. Это не четыре разных модели и не четыре полных независимых прохода по всей базе:

| Направление | Подробный результат | Замечания |
|---|---|---:|
| QR / «Рядом» / приглашения / отмены | [contacts.md](contacts.md) | 4 P2 + 2 P3 |
| Чаты / история / отправка / удаление / уведомления | [chat.md](chat.md) | 6 P2 + 2 P3 |
| Первый запуск / разрешения / связь / узел / настройки / debug | [settings.md](settings.md) | 5 P2 + 3 P3 |
| Общие компоненты / доступность / адаптация / визуальная база | [visual.md](visual.md) | 5 P2 + 2 P3 |
| Независимая проверка координатора | NAV-01 ниже | 1 P2 |

Координатор повторно прочитал основные UI-источники и цепочки, проверил, в частности, получение запроса Near/разрыв, асинхронную отправку и удаление, ограничение истории, маршрутизацию и статусные отображения. SQL-модель и контраст повторены независимо от финальных текстов субагентов. Подробные приложения сохранены для проверяемости аргументов и предложенных тестов; итоговая приоритизация и оговорки этого сводного документа имеют приоритет.

Начальные GitHub MCP-чтения части направлений встретили discovery failures/HTTP 429; работа продолжена по локальному клону того же SHA. Все четыре направления завершены. Частичный промежуточный отчёт чатов не публикуется как итог.

## NAV-01 — P2: пустой экран при неразрешившемся адресе маршрута

**Доказательство:** [`MainActivity.kt:185–227`](https://github.com/lineSence/secure-messenger/blob/0ccfbaa80eba483ea6c2cf6b83a6b80026235bae/android/app/src/main/java/dev/sm/messenger/MainActivity.kt#L185-L227).

**Условия:** Activity пересоздана с `route=chat:<address>` (либо info/verify); асинхронное чтение `book.list()` не завершилось или завершилось исключением. Другой вариант — маршрут указывает на контакт, которого нет в текущем читаемом списке.

**Actual:** `contacts` начинается с null; чтение через `runCatching(...).getOrNull()` оставляет null при отказе. `contactOf` возвращает null. Ветка `when` для маршрута уже выбрана, но `?.let` не рисует ничего; ветка вкладок `else` не выполняется. Нет loading/error/пояснения отсутствия контакта, retry, шапки или экранной кнопки назад. Пока чтение не выполнено, есть временная пустота; после отказа она может стать постоянной до внешнего изменения revision/выхода. Системный BackHandler остаётся рабочим — не заявляется, что приложение полностью невозможно покинуть.

**Expected:** loading до результата; recoverable error при ошибке чтения; отдельный «Контакт недоступен» при успешном чтении без адреса. Действия «Повторить» и «К чатам», без пересоздания ключей или удаления данных.

**Рекомендация:** явная модель Loading / Loaded / ReadError для разрешения маршрута. Не приравнивать временный storage failure к отсутствующему контакту и не стирать маршрут/данные молча.

**Регрессия:** ActivityScenario.restore/recreate с каждым из трёх маршрутов; задержать и затем сломать загрузку контактов; проверить progress → error/retry, успешный повтор и доступность назад. Отдельно успешный список без нужного адреса. Это статически установленная ветвь; настоящий Android-тест здесь не запускался.

## Дедупликация, известное и спорные границы

- **CHAT-05 — повторно подтверждённая известная проблема:** тот же порядок outbox→SQL фигурировал как AUD-12 в [security-аудите 2026-10-13](../2026-10-13/report.md). Здесь оценено пользовательское последствие ложного обещания «Ничего не изменено», не заявляется новая независимая уязвимость.
- **C-06 — уже известная проблема диагностики:** ADR-150/документация объясняли необходимость различения storage/network ошибок; debug-журнал реализован. Находка — сохранившееся неверное пользовательское сообщение, не отсутствие журнала.
- **C-03 — остаточный UX-пробел, не отрицание #89:** служебный обмен адресами реализован, ограничен по времени и может продолжаться через очередь. Проблема — передача его готовности/частичного результата в UI.
- **S04 — не старый зелёный Idle:** экран узла уже показывает «принят»; общий consumer NetStatus всё ещё отображает «Подключение…». S03 касается иных ветвей — ошибок подготовки и актуальности link.
- **CHAT-01 и S02 не дубли:** первый — подавление разрешённых уведомлений из-за lifecycle; второй — отсутствующий opt-in/индикация разрешения в новом потоке.
- **CHAT-02, CHAT-06 и NAV-01 различны:** ограничение успешно прочитанной истории; ложная пустота при отказе history; отсутствие самого экрана при отказе разрешения маршрута.
- **UI-02 не CHAT-07:** отсутствие невизуальной семантики шага доставки в пузыре и неправильный визуальный/текстовый статус Failed в списке исправляются отдельно.
- **UI-03 — унаследованная доступность палитры v14**, а не доказанное расхождение реализации с макетом. Расчёт: 2.472:1 для исходящих метаданных, 3.112:1 для входящих, 3.567:1 для белого текста primary-кнопки. Изменение палитры требует согласования, не самовольной смены стиля.
- **UI-04 и UI-05 — разные ограничения:** отсутствие прокрутки длинного тела и запрет переноса/роста самих кнопок. Точные пиксельные границы на Android не измерялись.
- **UI-07 — тестовый пробел, не отдельный пользовательский сбой.** Штатный стенд полезен для ручного сравнения. 52 объявления тестов × две темы = 104 сценария по исходнику, не число выполненных в этом аудите тестов.
- **S01 не предлагает вернуть секреты в Bundle:** текущее исключение из saved state учтено. Для rotation нужен scoped memory-state; политика process death должна быть явной и безопасной.
- Названия «ошибка сети»/«ошибка хранения» в разных подсистемах имеют общий принцип исправления, но C-06 и S05 оставлены разными случаями: независимые операции, разные исходные условия и разные ложные итоги.

## Актуальность дизайна и документации

Базовый визуальный язык — согласованный v14. Текущий код уже содержит новые потоки v16 из PR91; это видно и по diff, и по call sites. `wiki/architecture/ux.md` и `design/mockups/ui-v16.md` всё ещё говорят «предложено / код не изменён». Эти строки устарели в части факта реализации; из них **нельзя вывести отсутствие согласования владельца** и нельзя на их основании откатывать новый onboarding.

Аудит проверяет фактически реализованный новый поток, а не требует возврата старого мастера разрешений. Для новых исправлений нужно согласовать конкретные состояния/тексты, сохранив принятые компоненты. v15 (звонки) и прочие будущие возможности не превращаются в дефекты только потому, что отсутствуют.

Не считаются найденными багами: явно помеченные «Скоро»; демонстрационные данные вместо реальных; оговорённая будущая функциональность; отсутствие сообщения собеседнику об удалении; допустимый fallback без гостевого билета сам по себе; отсутствие отчётов о прочтении; корректный fail-closed при неоткрывающемся ключе.

## Очерёдность исправлений

1. **Сохранность и заметность сообщений:** CHAT-04, CHAT-01, CHAT-02, CHAT-05. Сначала fault/lifecycle/SQL-регрессии, затем минимальные изменения через PR. Подпись «ничего не изменено» допустима только при доказанной атомарности/восстановлении.
2. **Первое добавление без тупиков:** C-01, C-02, C-03, C-04, S01, S02. Отдельные понятия: контакт сохранён / адреса готовы / узел отвечает / сообщение доставлено. Не советовать повторно добавлять уже сохранённый контакт.
3. **Правдивые состояния и восстановление:** S03–S07, C-06, CHAT-06, NAV-01. Типизированные результаты и различимые Loading/Empty/Error; не выдавать запись конфигурации за работающую сеть.
4. **Чтение и доступность:** CHAT-03, CHAT-07/08, UI-01–06, C-05, S08. Ручная проверка небольшого экрана, крупного шрифта и TalkBack обязательна; не заменять её grep по размерам.
5. **Защита от повторных регрессий:** UI-07; deterministic reviewed baselines, verify-режим, конфигурационная matrix, тесты реальных листов и клавиатуры.

Рекомендации — предложения аудита, **не новые принятые ADR и не разрешение менять UI без макета**. Код — отдельными PR с зелёным `ci-ok`; проверки не ослаблять. Для изменений экранов действуют UI-MOCKUP-FIRST и UI-RENDER-CHECK, после локальных регрессий — проверка на двух телефонах.
