# Пять hot-path оптимизаций: реализация и повторные проверки

Дата: **2026-10-15 UTC**, по часам лаборатории. Основание — поручение владельца реализовать последовательность parser → FETCH route → reactor bookkeeping → zero-quota atomics → cleanup scheduler из [аудита регрессий](../2026-10-15-relay-regressions/report.md).

**Результат:** пять изменений реализованы и слиты [PR #97](https://github.com/lineSence/secure-messenger/pull/97). Head `92ad766c7cf5f4a29e899c7e2fd72a06a1cf7a78`, merge `b060fe85c3b117d209a8cc4116acbd84f56619ed`. [CI точного head](https://github.com/lineSence/secure-messenger/pull/97#issuecomment-6199119999) — все задачи success; перед merge подтверждён `mergeable_state=clean`.

CPU в смешанном 300-секундном окне: **64.68 → 59.22 мкс/завершённый цикл (-8.4%)**. Это улучшение относительно непосредственного main до PR #97, не доказательство устранения всей регрессии относительно старого thread-per-connection. В коротких повторах light CPU не улучшился при показанной точности. **p99 не улучшен во всех режимах**: MAX_BLOB немного выше и в длинном окне, и в медиане повторов; busy-короткие повторы также выше. Универсальное ускорение/окончательная стабилизация не заявлены.

Рабочий VPS и клиент не менялись. Wire v1/v2, RAM-only, абсолютные сроки, admission, подписи и запрет телеметрии сохранены. Измерения — только внешний синтетический стенд, не новые счётчики/логирование узла.

## 1. Что изменено

| Пункт | Реализация | Что сознательно не сделано |
|---|---|---|
| RA-01: parser state | Head с курсором поиска CRLF → Wire с проверенной HTTP length/close → Body с проверенными cmd/ID/version/offset/end. HTTP/wire заголовок не разбирается повторно при каждом фрагменте тела. Один 16-KiB scratch на worker; 256-KiB read budget на drive при прежнем пределе 32 итераций; явное перепланирование при исчерпании. | HTTP не расширен; Content-Length не доверяется до проверки. Входной drain/memmove payload ещё остаётся, это не zero-copy ingress. |
| RA-02: FETCH route | Одиночный FETCH: один SHA-256/маршрут, один shard guard для выборки и курсора. В обычном успешном SEND/FETCH/ACK — 2 SHA вместо 4. В списке маршруты ленивые, anchor повторно используется. WAIT держит конечный список до 64 маршрутов, subscribe-before-recheck сохранён. | Нет глобального кеша ID/истории, нового формата capability или одновременного захвата нескольких shards. |
| RA-03: reactor | Connection остаётся в HashMap; два ready HashSet и wake VecDeque переиспользуют capacity; таймер обновляется только при смене deadline. На Linux reregister только при смене READABLE/WRITABLE, недочитанное обслуживается через todo до WouldBlock/конечного бюджета. | Для остальных backend оставлен прежний reregister: их поведение не объявлено проверенным. Глобальный Registry lock/fan-out не устранён. |
| RA-04: нулевые quota atomics | take/give пропускают нулевой аргумент; Drop disarmed reservation больше не делает нулевых RMW. Сохраняются ненулевые CAS, прежний Ordering и полный RAII rollback. У обычной SEND/ACK пары 4 quota RMW вместо 9. | Счёт не включает Budget и Arc; общая квота не размножена по shards. |
| RA-05: cleanup scheduler | На shard — только atomic due/scheduled, обновляемые при отпускании guard без глобального scheduler mutex. Discovery ≤min(steps,256) атомарных посещений, полезная работа имеет отдельный steps budget. Уникальная очередь ≤S+1 с round-robin, try_lock занятого Store, chunks ≤16 Store steps и cooperative 2-ms лимит между chunks. | Это не жёсткое realtime-ограничение: единичный Store step/деструктор не прерывается. Все 4 внутренние линии Store сохранены; неиспользованный work quota не равен фактически освобождённым объектам. |

Начало полного discovery-прохода не требует обхода всех mutex. При S>256 discovery продолжается в следующих фоновых ходах. Новый due в уже просмотренном shard может ждать следующего discovery (обычная idle-пауза до секунды плюс продвижение сканирования). Busy shard возвращается в конец очереди; foreground никогда не берёт maintenance mutex. Backlog повторяется через 10 мс, без backlog — через 1 с. Служебное состояние планирования — не телеметрия.

Размеры временных структур остаются в действующих конечных runtime reservations: 16 KiB scratch в существующем worker stack reserve, списки/ready/decoder в per-connection reserve, scheduler в per-shard reserve. Это не новая полная оценка RSS, allocator/stack/OS-память отдельно не доказаны.

Пять пунктов выполнены одним связанным PR, а не пятью отдельно измеренными PR из исходного плана. Сравнение — эффект пакета; причинный выигрыш каждого пункта не выделен. Остальные RA-06…RA-14 не объявлены закрытыми (только reusable wake drain частично затронул RA-06).

## 3. Два окна по 300 секунд

База — `4edb5ca407ffa55af5c7f04dd7abc681e80c8eec` (relay-код прежнего a756a3d); новая версия — head PR #97. Одинаковый lab helper, release профиль и зависимости. SHA256 бинарников:
- до: `468671ab3c0c785c7aff1e79f822d09e0a1ea2b2f0fd8f52a2916d0a173f36f9`;
- после: `8506395813e8ce684e1f07fb876a26756194ca664aaff8e2ee1fce1f5c4cb414`.

2 CPU cgroup, co-located Python generator, localhost HTTP/wire v1, 2 reactor workers/16 data shards в обеих версиях, одинаковые квоты и synthetic payload. Порядок последовательно до → после; по 60 с: 5×4 KiB/2000 циклов·с, 32×4 KiB/6000, 16×131136 B/1000, 5 активных×4 KiB/2000 плюс 48 WAIT по 64 другим ID, 16×1 KiB/6000. Содержимое каждого SEND/FETCH и ACK проверено.

План 1,020,000 циклов на версию; выполнено **1,019,998 до**, **1,020,000 после**. Два не начатых пункта плана до — по одному busy/small у границы окна, не ошибки протокола и не выброшенные завершённые циклы. Завершения после границы: 10 до, 7 после, сохранены в выборке. Замер с drain: 300.009667/300.005558 с. Во всех попытках payload/status/ACK без ошибок; WAIT errors нет, stdout/stderr сервера после startup пусты.

CPU процесса: 65.97 → 60.40 CPU-с, или **64.68 → 59.22 мкс/цикл**. Генератор в этот CPU не входит; он конкурирует за те же CPU. Дискретность process CPU — 10 мс. Из-за двух не начатых циклов абсолютные completed не строго равны, отличие сохранено в знаменателях.

p99 с графиком = от запланированного начала SEND до окончания ACK, включая отставание генерации/обслуживания; service p99 = от фактического начала. Только завершённые циклы, все незапущенные пункты плана указаны выше. Не усредняем/не складываем p99:

| Профиль | p99 с отставанием, мс: до → после | p99 обслуживания, мс: до → после |
|---|---:|---:|
| 4 KiB · 5 | 0.364 → 0.365 | 0.288 → 0.289 |
| 4 KiB · 32 | 28.939 → 0.276 | 4.369 → 0.207 |
| 128 KiB+ · 16 | 0.612 → 0.630 | 0.536 → 0.552 |
| 4 KiB · 48 WAIT | 0.368 → 0.356 | 0.289 → 0.277 |
| 1 KiB · 16 | 77.227 → 0.328 | 3.144 → 0.252 |

**Остаточные ухудшения не скрыты:** light scheduled p99 почти тот же (+0.3%), MAX_BLOB +2.9% (service +3.0%). Большие снижения busy/small в этом окне **не универсальные −99% ускорения**: before имел крупные отставания, распределённые по окну, не только в разогреве. Например, >5 мс: busy 5884→105, small 11943→642; выбросы не удалены. Из общего sandbox нельзя однозначно отделить вклад узла, генератора и постороннего планирования. Следующий раздел показывает важный противоположный результат коротких повторов.

Внешний sampled peak RSS **3.06 → 3.02 MiB**, в обоих вариантах 3 потока (main+2 worker). Один sample/с и мало удерживаемых блобов — это не memory-exhaustion test и не доказательство полного RAM ceiling.

## 4. Отдельные повторы: 18×10 секунд

Три профиля × две версии × три повтора; порядок версий перемешан фиксированным seed на каждом повторе. Всего **540 000** завершённых циклов (все предложенные). Это отдельная популяция, не объединена с 300-секундным прогоном. Таблица — медианы трёх показателей прогона, не pooled percentile.

| Профиль | CPU до → после, мкс/цикл (медианы) | Δ CPU | p99 с графиком до → после, мс (медианы) |
|---|---:|---:|---:|
| 4 KiB · 5 | 61.50 → 61.50 | +0.0% | 0.323 → 0.338 |
| 4 KiB · 32 | 51.50 → 50.00 | -2.9% | 0.218 → 0.267 |
| MAX_BLOB · 16 | 139.00 → 120.00 | -13.7% | 0.584 → 0.597 |

| Профиль/версия | CPU min–max, мкс/цикл | p99 min–max, мс |
|---|---:|---:|
| 4 KiB · 5/before | 59.00–61.50 | 0.307–0.371 |
| 4 KiB · 5/after | 59.50–64.00 | 0.335–0.401 |
| 4 KiB · 32/before | 51.00–52.00 | 0.211–0.225 |
| 4 KiB · 32/after | 48.17–53.83 | 0.238–0.425 |
| MAX_BLOB · 16/before | 131.00–144.00 | 0.555–0.659 |
| MAX_BLOB · 16/after | 120.00–124.00 | 0.534–0.685 |

Light CPU медианно **без выигрыша**, busy около −2.9%, MAX_BLOB около −13.7%. Диапазоны light/busy пересекаются; три коротких повтора не дают заявления статистической значимости. p99 медианы **выше во всех трёх профилях**: light около +4.5%, busy около +22.6% (0.218→0.267 мс), MAX_BLOB около +2.3%. Busy — важный контрпример к огромному улучшению одного длинного окна. Следовательно, CPU-пакет принят, но цель «все регрессии latency устранены» не достигнута; нужны отдельный генератор/целевое железо и раздельные варианты настроек чтения/worker до фиксации.

## 5. Проверка механизмов отдельно от benchmark

`strace -f -c`: 2000 serial cycles 4 KiB или 400 MAX_BLOB, плюс startup/NEW/10 warmup. Ptrace меняет коалесцирование/планирование: его длительности/%time не latency и не доля CPU. EAGAIN/Interrupted при shutdown — ожидаемые syscall errors, не ошибки доставки.

| Вызов | 4 KiB до → после | MAX_BLOB до → после |
|---|---:|---:|
| recvfrom | 8109 → 8102 | 14087 → 4527 |
| epoll_ctl | 703 → 258 | 570 → 8 |
| epoll_wait | 701 → 693 | 569 → 269 |
| writev | 6031 → 6031 | 1231 → 1231 |

Локальная release cfg(test) probe: одна очередь, 1000 однобайтных блобов, now=168 h, Engine budget=256. Старые числа из предыдущего аудита той же алгоритмической базы, новый probe выполняется без foreground:

| Data shards | Вызовов maintain до | После |
|---:|---:|---:|
| 1 | 32 | 16 |
| 16 | 266 | 16 |
| 256 | 4013 | 16 |

Это **число вызовов**, не секунды и не обещание такого же времени при занятых locks. Проверка показывает снятие размывания useful-work budget пустыми разделами, но не полную матрицу fairness control/TTL под adversarial нагрузкой.

## 6. Ограничения и следующий этап

- Реализованы выбранные пять пунктов, не все оптимизации аудита. Остались глобальный notify Registry lock/fan-out, deque churn, часть ingress copies, синхронная auth/guest работа на I/O worker и др.
- Полная RSS/admission proof, длительный soak/ресурсное насыщение, proxy+TLS/WAN/физические телефоны не выполнены. Один shared-host A/B и три коротких повтора не определяют теоретический предел программы/число пользователей.
- Не заявлена полная ликвидация исходной CPU-регрессии PR #96 относительно pre-reactor: такой свежей трёхсторонней проверки не было. Нельзя сравнивать отдельные результаты разных дней как строго парные.
- Многоузловая маршрутизация и RAM-only HA 2/3 всё ещё не реализованы. Linux reregister path проверен локально/CI; другие backend сохраняют conservative behavior, но не прошли этот runtime benchmark.
- Узел/контракт окончательно не заморожены. В этом пакете снижение CPU оплачено небольшими/нестабильными изменениями p99; эти противоречия нужно учитывать, а не автоматически считать каждое удалённое действие улучшением latency.
